## What is an Event Bus?

An **Event Bus** is a software architecture component that lets different applications, services, or modules communicate by **publishing and receiving events**, without needing to talk to each other directly.

A service publishes an event such as `OrderPlaced`. The Event Bus receives it and routes it to whichever services are interested — the publisher never has to know who those are.

<MermaidDiagram title="The Core Pattern" chart={`
flowchart LR
  A[Order Service] -->|OrderPlaced| B((Event Bus))
  B --> C[Service A]
  B --> D[Service B]
  B --> E[Service C]
`} />

## What is an Event?

An **event** is a record that something has happened. It's a fact, already in the past — `UserRegistered`, `OrderCreated`, `PaymentCompleted`, `PaymentFailed`, `ProductPurchased`, `InvoiceGenerated`, `FileUploaded`, `LoanApproved`, `TransactionCompleted`.

```json
{
  "eventType": "OrderPlaced",
  "eventId": "evt-1001",
  "timestamp": "2026-09-19T12:30:00Z",
  "data": {
    "orderId": "ORD-5001",
    "customerId": "C-100",
    "amount": 5000
  }
}
```

> **Core idea:** An event describes something that has *already* happened.

## The coupling problem

Imagine an application with many services — Customer, Order, Payment, Inventory, Email, Notification, Analytics, Fraud, Shipping, Accounting. Without a bus, the Order Service has to know about, and call, every one of them directly. That's **tight coupling**. With a bus, it just announces what happened.

<MermaidDiagram title="Without a Bus — Tight Coupling" chart={`
flowchart LR
  O[Order Service] -.-> P[Payment]
  O -.-> I[Inventory]
  O -.-> E[Email]
  O -.-> F[Fraud]
  O -.-> A[Analytics]
`} />

<MermaidDiagram title="With a Bus — Decoupled" chart={`
flowchart LR
  O[Order Service] -->|publish| B((Event Bus))
  B --> P[Payment]
  B --> I[Inventory]
  B --> E[Email]
  B --> F[Fraud]
  B --> A[Analytics]
`} />

## The four main components

Every event-driven exchange reduces to the same four parts.

<MermaidDiagram title="Producer -> Event -> Event Bus -> Consumer(s)" chart={`
flowchart LR
  P[Producer] --> Ev[/Event/]
  Ev --> B((Event Bus))
  B --> C[Consumer(s)]
`} />

- **Producer** — the Order Service creates the event and publishes `OrderPlaced`.
- **Event** — the payload describing what happened.
- **Event Bus** — receives it and decides where it should go.
- **Consumer** — a service that receives and processes it.

Email Service and Inventory Service can both listen for `OrderPlaced` and react independently, with no awareness of each other.

## Why use an Event Bus?

The major reason is **decoupling**. The Order Service only needs to know: "I published `OrderPlaced`." It does not need to know who is listening.

- Loose coupling
- Asynchronous communication
- Scalability
- Easier extensibility
- Failure isolation
- Independent service development
- Event routing
- Distributed integration

## Event Bus vs. direct API call

A direct API call is the Order Service asking the Payment Service to do something, and waiting. An event bus call is an announcement — the publisher doesn't necessarily care who reacts, or when.

`} />

<MermaidDiagram title="Event Bus — Asynchronous" chart={`

## Event Bus vs. message queue

A **queue** is work waiting to be picked up by one of several competing workers — 1,000 image-processing jobs split across a worker pool. An Event Bus is **publish/subscribe**: every interested subscriber gets its own copy of the same event.

<MermaidDiagram title="Queue — One Job, One Worker" chart={`
flowchart LR
  Q((Queue)) --> W1[Worker]
  Q -.-> W2[Worker]
  Q -.-> W3[Worker]
`} />

<MermaidDiagram title="Pub/Sub — Every Subscriber Gets a Copy" chart={`
flowchart LR
  Ev[Event] --> B((Event Bus))
  B --> E1[Email]
  B --> F1[Fraud]
  B --> A1[Analytics]
`} />

> **Rule of thumb:** Queue: "Someone needs to process this job." Event Bus: "Something happened; interested services can react."

## Event Bus vs. event stream

An Event Bus is mostly about **routing** a discrete event to interested consumers. An event stream is a continuous, ordered sequence — the domain Kafka is built for.

<MermaidDiagram title="Event -> Router -> Consumers" chart={`
flowchart LR
  Ev[Event] --> R((Router))
  R --> C[Consumers]
`} />

An event stream, by contrast, is a continuous sequence:

```text
Event 1 -> Event 2 -> Event 3 -> Event 4 -> Event 5 -> ...continuous stream
```

## Routing

One of the most powerful capabilities of an Event Bus is routing by rule — it isn't merely a pipe. Given a `PaymentCompleted` event, several independent rules can each decide where a copy should go.

```json
{
  "type": "PaymentCompleted",
  "amount": 100000,
  "currency": "PKR"
}
```

<MermaidDiagram title="Each Rule Evaluates Independently" chart={`
flowchart LR
  Ev["PaymentCompleted (amount, currency)"] --> B((Event Bus))
  B -->|"type = Payment..."| A1[Accounting Service]
  B -->|"amount > 50000"| F1[Fraud Detection]
  B -->|"currency = USD"| C1[Currency Analytics]
`} />

## A complete e-commerce example

A customer buys a product. The Order Service creates `Order #1001` and publishes a single event — five independent services pick it up and each do their own job, with no direct calls between any of them.

```json
{
  "eventType": "OrderPlaced",
  "eventId": "evt-1001",
  "data": {
    "orderId": "1001",
    "customerId": "C123",
    "productId": "P500",
    "quantity": 2,
    "amount": 10000
  }
}
```

<MermaidDiagram title="One Publish, Five Independent Reactions" chart={`

## Scalability

Consumers scale independently of each other. This matters most when workloads differ wildly between services.

<MermaidDiagram title="Each Consumer Runs Its Own Worker Count" chart={`
flowchart LR
  B((Event Bus)) --> E["Email (x10 workers)"]
  B --> F["Fraud (x20 workers)"]
  B --> A["Analytics (x5 workers)"]

## Asynchronous processing

Some operations don't need to block the original request. The customer gets a response as soon as the order is created — email, analytics, and recommendations run afterward, in the background.

**Foreground:** `Order created -> Response returned`

**Background:** `Email`, `Analytics`, `Recommendation`

## Duplicates and idempotency

A consumer may receive the same event more than once. It needs to recognize a repeat and skip it — commonly by tracking which `eventId` values it has already processed. This is one of the most important concepts in reliable event-driven systems.

<MermaidDiagram title="Check the Event ID Before Acting on It" chart={`
flowchart LR
  Ev["OrderPlaced (evt-1001)"] --> Q{Already processed?}
  Q -->|yes| Ig[Ignore duplicate]
  Q -->|no| Pr[Process + record]
`} />

```text
if eventId already processed:
    ignore duplicate
else:
    process event
    record eventId
```

## Event ordering

If `PaymentCompleted` arrives before `OrderPlaced`, a consumer that expects the opposite order can break. Ordering behavior depends entirely on the technology and configuration — not every bus or messaging system guarantees it globally.

**Out of order — a problem:** `PaymentCompleted -> OrderPlaced`

**Expected order:** `OrderPlaced -> PaymentCompleted`

## Failure handling

When a consumer is temporarily unavailable, a production system leans on retries, backoff, monitoring, and alerting. A **Dead-Letter Queue (DLQ)** catches messages that still fail after the configured attempts.

<MermaidDiagram title="A Down Consumer Routes to Retry, Then DLQ" chart={`
flowchart LR
  B((Event Bus)) --> P["Payment Service (temporarily down)"]
  P --> R["Retry -> Dead-Letter Queue"]
`} />

## Event schema

One of the most important aspects of event-driven systems is the **event contract**. If one service publishes `customer` and another expects `customerId`, you have a compatibility problem before any logic even runs.

| Service A publishes | Service B expects |
|---|---|
| `{ "customer": 123 }` | `{ "customerId": 123 }` |

A better approach is an explicit, versioned schema, so every consumer gets a predictable contract:

```json
{
  "eventType": "OrderPlaced",
  "version": "1.0",
  "eventId": "evt-1001",
  "timestamp": "...",
  "data": { "orderId": "ORD-1" }
}
```

## Event versioning

When `currency` is added to an already-published event shape, backward compatibility matters. Two common approaches: a versioned type name like `OrderPlaced.v2`, or an explicit `version` field.

`OrderPlaced.v1 -> OrderPlaced.v2`

> **Principle:** Good event-driven architecture treats events as contracts between independently evolving systems.

## Security

Production systems need clear answers to who can publish, who can subscribe, who can read events, and who can create or modify routing rules — typically via authentication, RBAC, encryption in transit and at rest, secrets management, audit logging, schema validation, and tenant isolation.

<MermaidDiagram title="Publish and Subscribe Rights Are Explicit, Per Service" chart={`
flowchart LR
  O[Order Service] -->|publish OrderPlaced| B((Event Bus))
  B -->|allowed| P[Payment Service]
  B -->|allowed| I[Inventory]
  B -.->|denied| R[Random Service]
`} />

## An Event Bus is not a database

A database answers "what data do we have?" An Event Bus answers "which consumers should receive this?" They work together, not in competition.

| Database | Event Bus |
|---|---|
| Customers | OrderCreated |
| Orders | PaymentCompleted |
| Payments | ProductUpdated |
| Products | CustomerRegistered |

## Event Bus in banking

A transfer's core transaction is typically handled synchronously — but once it commits, the fallout (notifications, fraud checks, analytics) can safely happen asynchronously. Financial systems demand especially careful consistency, ordering, idempotency, authorization, auditing, and failure recovery.

## Core Event Bus architecture

A realistic conceptual architecture: an event source feeds the bus, which applies rules and transformation, and routes matching events on to consumers that each write to their own store.

<MermaidDiagram title="Source -> Bus -> Rules / Transform -> Consumers -> Stores" chart={`

  Ru --> Cc[Consumer C] --> An1[Analytics]
`} />

## The most important mental model

Don't think of an Event Bus as just a complicated server. Think of it as a communication and routing mechanism where producers publish events and interested consumers react to them.

<MermaidDiagram title="The Fundamental Pattern, In Full" chart={`
flowchart LR
  P[Producer] -->|publishes event| B((Event Bus))
  B --> Ru[routing rules]
  Ru --> A[Consumer A]
  Ru --> Bb[Consumer B]
  Ru --> Cc[Consumer C]
`} />

> **The property that matters most:** The producer does not need to know all the consumers.

## One-line definition, for interviews

> An Event Bus is a **middleware component** that receives events from producers, routes them by rule or subscription, and delivers them **asynchronously** to one or more consumers — enabling loosely coupled, event-driven systems.

## Quick comparison table

| Concept | Main idea |
|---|---|
| REST API | Direct request / response |
| gRPC | Direct, high-performance service communication |
| Queue | Work waiting to be processed |
| Pub/Sub | One message can reach multiple subscribers |
| Event Bus | Routes events to interested consumers |
| Event Stream | Continuous sequence of events |
| Event Sourcing | Store state changes as events |
| CQRS | Separate read and write models |
| Saga | Coordinate distributed business transactions |

## Final summary

<MermaidDiagram title="Something Happens, and Independent Parts React" chart={`
flowchart LR
  W[Something happened] --> P[Producer]
  P --> B((Event Bus))
  B --> Ru[routing / rules]
  Ru --> A[Consumer A] --> A2[Action]
  Ru --> Bb[Consumer B] --> B2[Action]
  Ru --> Cc[Consumer C] --> C2[Action]

> **In one sentence:** An Event Bus lets one part of a distributed system announce that something happened, while allowing multiple independent parts of the system to react — without the original producer ever having to know about them.
