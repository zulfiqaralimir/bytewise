# System Design Patterns You Should Master

Five patterns that show up again and again once a system grows past "one server, one database." No prior programming background needed here — we're talking about how the pieces of a system are arranged, not how to code them.

Wherever a pattern leans on a computer-science idea underneath — a data structure, an algorithm, a classic technique — you'll see a **DSA / Algorithm Angle** note. And wherever real products use the pattern, you'll see a **Where You'll See This** note.

## 1. Monolith vs. Microservices

**The first fork in the road for almost every system.**

Before you design anything else, you have to answer one question: does your whole backend live in one codebase, one server (a **monolith**), or is it split into small, independent services that each own one job (**microservices**)?

In a monolith, your authentication code, your notification code, and your comments code all sit inside the same big program. It's simple to reason about and simple to run. But it has one weakness: if the notification part of the code has a bug and crashes, it can take the *entire server* down with it — comments and login included.

Microservices fix that by giving every feature its own small, independently-running service — an Auth service, a Notification service, a Comment service, each possibly written in a different language, deployed separately, and scaled separately. If Notifications goes down, Auth and Comments keep working. The cost is that you now have several small systems to deploy, monitor, and — the tricky part — get talking to each other.

> **Trade-off:** Monolith — easy to run, but one bug can take the whole app down, and you can't scale just the busy part. Microservices — fault-isolated and independently scalable, but now you must design how services find and talk to each other over the network.

> **DSA / Algorithm Angle:** Splitting into services doesn't need a specific algorithm by itself, but it opens the door to ones you'll meet soon after: **load balancing algorithms** (round robin, least-connections, consistent hashing) to spread traffic across copies of a service, and **service-discovery** lookups (essentially hash-table lookups by service name) so services can find each other.

> **Where You'll See This:** Large-scale consumer platforms — ride-hailing apps, large e-commerce marketplaces, video streaming services — run on microservices, because a single team needs to ship and scale their one feature without waiting on, or breaking, everyone else's. Smaller products and early-stage startups usually start as a monolith on purpose, because it's faster to build and easier for a small team to manage.

## 2. Database-per-Service

**Once you split the code, do you also split the data?**

Say you've gone with microservices: an Auth service, a File-Upload service, a Notification service. The natural next question is — do they all share *one* database, or does each service get its *own*?

Sharing one database is tempting: it's simpler, and services that need the same data (like user details) can just read the same tables. But it quietly breaks the whole point of microservices. Your code is separated, but your data isn't — a bug in the Notification service could still accidentally delete a row in the Users table. That's not real isolation.

**Database-per-service** says: give every service its own database, and let it pick whatever type fits its job. An Auth service might use a document database because its schema keeps changing. A Notification service tracking click-rates and opens might use a fast analytics database. A Posts service with clearly structured data might use a classic relational database. Each one is optimized for what it actually does.

> **Trade-off:** True isolation and the freedom to pick the right database per service — at the cost of more infrastructure to run, and no more cross-service database joins. If the Post service needs a user's name, it has to *ask* the Auth service for it and combine the results itself.

> **DSA / Algorithm Angle:** Since the database can no longer join two tables for you, your application code effectively performs the join itself — conceptually the same as an in-memory **hash join**: fetch one dataset, build a lookup structure (a hash map) keyed by ID, then match it against the second dataset.

> **Where You'll See This:** Any large microservices platform that's serious about fault isolation uses this — payments, identity, and messaging systems inside big tech companies each keep their own dedicated data store, precisely so a bug in one can never directly corrupt another's data.

## 3. Circuit Breaker

**Stopping one dead service from taking the rest down with it.**

Now that services depend on each other, here's the nightmare scenario: Service A calls Service B, which calls Service C. If C goes down, B keeps waiting on it and eventually fails too. Then A, waiting on B, fails as well. One dead service just **cascaded** into three dead services.

A circuit breaker <Revision>sits between two services like a proxy</Revision> and borrows its name from an electrical circuit breaker. While the downstream service is healthy, the "circuit" stays **closed** and requests flow through normally. The moment it notices failures piling up past a threshold, it **opens** the circuit — it stops sending requests altogether and fails fast, instead of letting everyone wait on a service that's already struggling. After a cooldown period, it goes **half-open**: it lets through one test request to check if the service has recovered. If that succeeds, the circuit closes again; if not, it reopens and waits longer.

> **DSA / Algorithm Angle:** This pattern *is*, almost literally, a textbook **finite state machine (FSM)** — a foundational computer-science structure with a fixed set of states (closed / open / half-open) and defined transitions between them triggered by events (failure count, timeout, test result). If you've studied automata theory, this is that idea applied directly to production traffic.

> **Where You'll See This:** Netflix popularized this pattern at scale with its open-source **Hystrix** library, built specifically to stop one failing dependency from cascading across its streaming backend. It's now a standard tool in most microservice frameworks and <Revision>API gateways for exactly this reason.</Revision>

## 4. Event Sourcing

**Stop overwriting state — start recording what happened.**

The usual way to track something's status is to store one row with a "current state" column, and overwrite it every time something changes: an order goes from *placed* → *shipped* → *delivered*, mutating the same field each time. That's simple, but at high volume — think a banking system processing constant transactions, or an e-commerce platform placing thousands of orders a second — constantly locking and rewriting that one row becomes a bottleneck.

**Event sourcing** flips the idea: instead of overwriting state, you **append** an immutable event every time something happens, and never delete or edit past events. "Order placed at 12:00." "Ready to ship at 12:05." "Shipped at 12:10." "Delivered at 12:30." If you want to know an order's current status, <Revision>you read through its event log and take the latest entry.</Revision> <Revision>The event log itself becomes your source of truth.</Revision>

> **DSA / Algorithm Angle:** An event log is structurally a <Revision>simple **append-only sequence** (think of it as a linked list you only ever add to at the tail)</Revision>. Computing "current state" from it is a classic **fold / reduce** operation — walking the sequence once and combining events into a final result, the same operation <Revision>used in functional programming and MapReduce-style pipelines.</Revision> It's also the same underlying idea as a database's **write-ahead log (WAL)**, which many databases already use internally for durability.

> **Where You'll See This:** Banking and accounting systems have used this idea for centuries in the form of <Revision>double-entry ledgers</Revision> — balances are computed from a list of transactions, never overwritten. In modern engineering, **Kafka** is the tool most commonly used to build this kind of <Revision>append-only event backbone, and version control systems like **Git** are,</Revision> conceptually, event sourcing applied to your codebase — your repository's state is just the replay of every commit.

## 5. CQRS

**Command Query Responsibility Segregation — stop writes and reads from fighting over the same table.**

Once you have an event log in place, a natural next step follows. At Amazon-level scale, you can't have every single write and every single read hitting the same database table — it becomes the bottleneck for the entire system. **CQRS** says: separate the two paths entirely. Give **writes** (commands — create, update, delete) their own path, and give **reads** (queries) a completely separate one.

In practice: a write comes in, gets turned into an event, and lands in the event log. A background process reads that log, reshapes ("denormalizes") the data into a form that's fast to query, and updates a separate **read database**. Anyone who wants to read data goes straight to that read database — it's always ready, and it never competes with writes for the same resources.

> **Trade-off:** The read database is updated slightly after the write happens — this is called **eventual consistency**. If your system can tolerate a brief lag between "I wrote this" and "I can read this," CQRS is a strong fit. If it can't (say, a bank balance check), it needs more care.

> **DSA / Algorithm Angle:** The read database is essentially a **materialized view** — a precomputed, denormalized result kept up to date incrementally, so a query never has to redo the same computation from scratch. That "read straight from a pre-shaped table" idea is the same reasoning behind caching and indexing structures in general: do the expensive work once, look it up cheaply many times.

> **Where You'll See This:** CQRS pairs naturally with event sourcing and shows up wherever reads vastly outnumber writes — social media feeds, e-commerce product catalogs, and real-time leaderboards in large multiplayer games are classic examples, since they all serve enormous read traffic against comparatively few writes.

## How These Five Connect

1. **Monolith vs. Microservices** — the first decision: one codebase, or many independent services?
2. **Database-per-Service** — if you chose microservices, do the services also get separate databases?
3. **Circuit Breaker** — now that services depend on each other, how do you stop one failure from cascading?
4. **Event Sourcing** — at high write volume, how do you record state without a single table becoming a bottleneck?
5. **CQRS** — once you have an event log, how do you also keep reads fast and separate from writes?

## Summary

- A **monolith** is simple to run but shares fate — one bug can take everything down. **Microservices** isolate failures but require services to find and call each other.
- **Database-per-service** gives every service full data isolation and the freedom to pick the right database type, at the cost of losing cross-service database joins.
- A **circuit breaker** stops one failing service from cascading into failures upstream, by tracking closed/open/half-open state and failing fast once a threshold is crossed.
- **Event sourcing** replaces "overwrite the current state" with "append an immutable event," turning the event log itself into the source of truth.
- **CQRS** separates the write path (commands, through the event log) from the read path (queries, against a pre-shaped read database), trading a small consistency delay for reads that never compete with writes.
- These five patterns build on each other: the more you split a system apart for scale and fault isolation, the more you need mechanisms — circuit breakers, event logs, denormalized read stores — to keep it coherent and fast.
