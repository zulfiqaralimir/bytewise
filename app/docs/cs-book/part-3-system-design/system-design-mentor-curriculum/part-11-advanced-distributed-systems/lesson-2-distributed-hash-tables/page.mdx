# Lesson 2 — Distributed Hash Tables (DHTs)

## 1. First: What Is a Hash Table?

A normal hash table stores data as:

```text
Key       Value
----------------
101   →   Ali
102   →   Ahmed
103   →   Sara
```

A hash function helps us quickly determine where a key/value should be stored:

```text
Key → Hash → Location → Value
```

Normally, the hash table could exist on **one computer**.

## 2. The Problem

Imagine we have **1 billion pieces of data**. One computer may not have enough storage, memory, CPU, or network capacity. So we distribute the data across multiple computers:

<MermaidDiagram title="Distributing Data Across Nodes" chart={`
graph TD
  Data --> A[Node A]
  Data --> B[Node B]
  Data --> C[Node C]
`} />

Here, **node = a computer participating in the distributed system.**

Now we have a new problem:

> **When I have a key, how do I know which node contains its data?**

This is where a **Distributed Hash Table (DHT)** comes in.

## 3. What Is a DHT?

**DHT = Distributed Hash Table.**

> **A DHT is a hash-table-like system whose data is distributed across many computers and which provides a mechanism for locating the node responsible for a particular key.**

In simple words:

> **DHT = Hash Table distributed among many computers.**

<MermaidDiagram title="A DHT Spreads the Table Across Nodes" chart={`
graph TD
  DHT --> A[Node A]
  DHT --> B[Node B]
  DHT --> C[Node C]
`} />

## 4. Simple Example

Suppose we have `Node A`, `Node B`, `Node C`, and keys `Apple`, `Banana`, `Mango`. The DHT uses a hashing/assignment mechanism to determine which node is responsible for each key:

```text
Apple  → Node B
Banana → Node A
Mango  → Node C
```

If we want Banana:

<MermaidDiagram title="Looking Up Banana" chart={`
graph TD
  Banana --> L["Hash / DHT Lookup"]
  L --> NA[Node A]
  NA --> D["Banana's Data"]
`} />

The important point is: **the DHT helps determine the responsible node.**

## 5. What Does "Distributed" Mean?

It means the data is spread across multiple computers:

```text
Node A → Data 1, Data 4, Data 7
Node B → Data 2, Data 5, Data 8
Node C → Data 3, Data 6, Data 9
```

The data is **distributed**.

## 6. What Does "Decentralized" Mean?

This is different from simply being distributed.

**Centralized** — one central server coordinates the system and may know where everything is:

<MermaidDiagram title="Centralized" chart={`
graph TD
  CS[Central Server] --> A[Node A]
  CS --> B[Node B]
  CS --> C[Node C]
`} />

If that central server fails, it can become a major problem.

**Decentralized** — participating nodes themselves take part in maintaining the distributed lookup system, and there is **no single central server that must handle every lookup**:

<MermaidDiagram title="Decentralized" chart={`
graph LR
  A[Node A] --- B[Node B]
  A --- C[Node C]
  B --- D[Node D]
  C --- D
`} />

So remember:

> **Distributed = work/data is spread across many computers.**
>
> **Decentralized = there is no single central server responsible for everything.**

A system can be distributed without being fully decentralized.

## 7. DHT vs. Routing

This is extremely important — they are related, but they are **not the same thing**.

Suppose you want `Key = "Ali"`. The DHT determines the responsible node:

<MermaidDiagram title="DHT Lookup" chart={`
graph TD
  Ali["Key: Ali"] --> L["DHT Lookup"]
  L --> NC["Responsible Node = C"]
`} />

But suppose you are currently connected to Node A, and you need to reach Node C. The process of moving the request from one node to another is **routing**:

<MermaidDiagram title="Routing the Request" chart={`
graph LR
  You --> NA[Node A]
  NA --> NB[Node B]
  NB --> NC[Node C]
`} />

Therefore:

- **DHT:** "Which node is responsible for this key?"
- **Routing:** "How do I get the request to that node?"

## 8. Real-Life Analogy — Google Maps

Imagine you want to travel to Islamabad Airport.

**Finding the destination** — you determine that Islamabad Airport is your destination. This is similar to **DHT lookup**: `Key → Responsible Node`.

**Finding the route** — now you need to travel from your location, down Road A, down Road B, to the airport. This is similar to **routing**:

<MermaidDiagram title="Reaching the Destination" chart={`
graph LR
  Loc["Your Location"] --> RA["Road A"]
  RA --> RB["Road B"]
  RB --> Airport
`} />

So remember:

> **DHT helps identify the destination.**
>
> **Routing helps reach the destination.**

## 9. How Does Hashing Help?

A hash function converts a key into an identifier, and nodes also have identifiers (`Node A → 200`, `Node B → 500`, `Node C → 800`). The DHT's rules determine which node is responsible for a given identifier:

<MermaidDiagram title="From Key to Responsible Node" chart={`
graph TD
  Ali2["Key: Ali"] --> H["Hash Function"]
  H --> ID["Identifier = 730"]
  ID --> DHT2[DHT]
  DHT2 --> NC2[Node C]
`} />

So hashing helps create a **deterministic way to map keys to nodes**.

## 10. What Happens When a Node Fails?

Suppose Node B fails. An important correction:

> **A DHT does NOT automatically mean the data is safe when a node fails.**

If the only copy of `Data X` was on Node B, and Node B dies, `Data X` may be unavailable. So we need another concept:

### Replication

Replication means keeping **additional copies of the same data**:

<MermaidDiagram title="Replication: A Backup Copy" chart={`
graph TD
  X["Data X"] --> Primary["Node B — Primary"]
  X --> Replica["Node C — Replica"]
`} />

If Node B fails, the system may retrieve the data from Node C. Therefore:

> **DHT = helps locate data.**
>
> **Replication = keeps additional copies of data.**

They are different concepts.

## 11. Does Every DHT Use Replication?

**No.** A DHT's fundamental purpose is **distributed lookup**. A particular DHT-based system may additionally use replication for fault tolerance, availability, or data durability.

So do NOT memorize `DHT = Replication`. Instead remember:

```text
DHT         → Find the responsible node
Routing     → Reach that node
Replication → Keep additional copies
```

## 12. DHT and Consistent Hashing

You learned **Consistent Hashing** in Lesson 1. They are related, but they are not identical.

**Consistent Hashing** primarily provides a way to distribute keys among servers — it is particularly useful because adding/removing servers causes relatively little key movement:

```text
Key → Hash → Hash Ring → Responsible Server
```

**DHT** provides a **distributed lookup system**:

```text
Key → DHT Lookup → Responsible Node → Value
```

Some DHTs use ideas related to consistent hashing. But:

> **Consistent hashing is a technique.**
>
> **DHT is a distributed lookup system/protocol.**

## 13. Programming Connection

A real DHT implementation combines several areas of computer science: hashing (key → identifier), networking (nodes must communicate), routing (nodes forward requests), and data storage (the responsible node stores the data):

<MermaidDiagram title="What a Real DHT Implementation Involves" chart={`
graph TD
  H2[Hashing] --> DHT3[DHT]
  N2[Networking] --> DHT3
  R2[Routing] --> DHT3
  DS[Data Storage] --> DHT3
`} />

This does NOT mean these are four separate DHTs — it means a real DHT implementation involves all of these areas together.

## 14. Complete Picture

Suppose you want `Key = "Ali"`. The complete process, including a replica for safety, looks like this:

<MermaidDiagram title="The Complete Lookup Path" chart={`
graph TD
  Ali3["Key: Ali"] --> Hash2[Hashing]
  Hash2 --> Lookup2["DHT Lookup"]
  Lookup2 --> Resp["Responsible Node = C"]
  Resp --> Route2["Routing: A → B → C"]
  Route2 --> NodeC[Node C]
  NodeC --> Data2[Data]
  NodeC --> Replica2["Replica on Node D"]
`} />

If Node C fails, the data is still available from the replica on Node D.

## 15. The Four Concepts You Must Keep Separate

| Concept | Main Job |
|---|---|
| **Hashing** | Converts a key into an identifier |
| **DHT** | Determines/locates the responsible node |
| **Routing** | Moves the request toward that node |
| **Replication** | Keeps additional copies of data |

**Easy memory trick:**

> **Hash → Find → Route → Retrieve**
>
> **Replication → Backup copy for failure**

## 16. Real-World Connection

DHTs are strongly associated with **peer-to-peer (P2P) systems**. For example, BitTorrent uses DHT mechanisms for peer discovery:

<MermaidDiagram title="DHT in a P2P File Download" chart={`
graph TD
  Want["You Want a File"] --> Lookup3["DHT Lookup"]
  Lookup3 --> Peers["Find Peers"]
  Peers --> Connect["Connect to Peers"]
  Connect --> Download
`} />

<Revision>Instead of relying completely on one central server, participating computers can help maintain the distributed lookup system.</Revision>

## Webbook Revision

**DHT — one-line definition:**

> <Revision>**A Distributed Hash Table (DHT) is a decentralized distributed system that spreads key-value data across many nodes and provides an efficient mechanism for locating the node responsible for a key.**</Revision>

**Remember:**

```text
Hash Table
Key → Value

Consistent Hashing
Key → Server

DHT
Key → Responsible Node → Value

Routing
Current Node → Next Node → Destination

Replication
Data → Copy 1 + Copy 2 + Copy 3
```

**Most important distinction:**

- **DHT:** Where is the data?
- **Routing:** How do I reach that node?
- **Replication:** What if that node fails?
- **Decentralization:** No single central server has to handle everything.

**Memory trick:**

> **DHT finds the destination; routing reaches the destination; replication protects the data.**
