We previously saw a problem:

> What if the servers are **not evenly distributed** on the hash ring?

Server A might receive a very large portion of the keys, while B and C receive very few. That creates a **load imbalance**.

## The Solution: Virtual Nodes

Instead of putting each physical server on the ring only once, we put it **multiple times**:

```text
Server A → A1, A2, A3
Server B → B1, B2, B3
Server C → C1, C2, C3
```

These are called **virtual nodes (vnodes)**. Each virtual node still belongs to a physical server — it's just another position on the ring.

### Mapping Virtual Nodes Back to Physical Servers

<MermaidDiagram title="Virtual Nodes → Physical Servers" chart={`
graph LR
  A1 --> SA[Physical Server A]
  A2 --> SA
  A3 --> SA
  B1 --> SB[Physical Server B]
  B2 --> SB
  B3 --> SB
  C1 --> SC[Physical Server C]
  C2 --> SC
  C3 --> SC
`} />

### Why Do We Do This?

Because it makes the workload **more evenly distributed**.

- Without virtual nodes: one server could accidentally get too much data.
- With virtual nodes: the data is spread across many positions, giving a more balanced distribution.

### A Very Important Distinction

- **Physical server** = the actual machine.
- **Virtual node** = a position on the hash ring representing that server.

## What Happens When Server B Fails?

Because B has several virtual nodes — `B1`, `B2`, `B3` — the keys belonging to those positions can be reassigned to neighboring servers instead of the whole ring being reshuffled:

<MermaidDiagram title="Server B Fails — Its Virtual Nodes Fall to Their Neighbors" chart={`
graph LR
  B1[B1] --> SA[Server A]
  B2[B2] --> SC[Server C]
  B3[B3] --> SA2[Server A]
`} />

We don't have to reorganize the entire system — only the small arcs that belonged to `B1`, `B2`, and `B3` move, each to whichever server is now next clockwise.

## Webbook Revision

> **Virtual nodes:** multiple positions on the consistent-hashing ring assigned to each physical server, to improve load distribution and make server addition/removal smoother.

**Memory trick:**

> **One physical server gets many virtual positions → better balance.**
