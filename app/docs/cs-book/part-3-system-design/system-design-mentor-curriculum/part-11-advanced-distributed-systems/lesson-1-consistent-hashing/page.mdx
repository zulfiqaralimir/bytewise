# Lesson 1 — Consistent Hashing

Let's start from **zero**, because consistent hashing becomes easy once you understand the problem it solves.

## 1. What Problem Are We Trying to Solve?

Imagine we have **3 servers** storing cached data:

```text
Server A
Server B
Server C
```

We need to decide:

> **Where should a particular user's data go?**

A simple approach is:

```text
server = hash(user_id) % 3
```

For example:

```text
User 101 → hash → 0 → Server A
User 102 → hash → 1 → Server B
User 103 → hash → 2 → Server C
```

This works nicely.

### But Now Server D Is Added

We now calculate:

```text
hash(user_id) % 4
```

The results change for **many users**. Data that was previously:

```text
User 101 → Server A
```

might now become:

```text
User 101 → Server C
```

That means the system has to **move and rebuild a huge amount of cached data**.

This is the problem **consistent hashing** tries to solve.

## 2. What Is Consistent Hashing?

**Consistent hashing is a technique for distributing data across multiple servers while minimizing the amount of data that needs to move when servers are added or removed.**

The key idea:

> **When the number of servers changes, only a relatively small portion of the data needs to move.**

## 3. The Basic Logic

Instead of using:

```text
hash(key) % number_of_servers
```

we create a **hash ring** — think of it like a circular clock, wrapping from 359° straight back around to 0°:

Both **servers** and **data keys** are placed on this same ring, using the same hash function. The rule is:

> Hash the data key → find its position on the ring → move clockwise → the first server you encounter owns that data.

Only the data sitting between Server D's new position and its nearest predecessor needs to move. **We don't have to redistribute everything** — that's the major advantage.

## 6. Why Is This Important in System Design?

This is particularly useful when we have **distributed caches or distributed storage**:

<MermaidDiagram title="Where the Ring Sits in the Stack" chart={`
graph TD
  U[Users] --> AS[Application Servers]
  AS --> DC[Distributed Cache]
  DC --> A[Server A]
  DC --> B[Server B]
  DC --> C[Server C]
`} />

If we add another cache server (`Server D`), we want to avoid completely rearranging the cache. **Consistent hashing minimizes that movement.**

## 7. Where Is Consistent Hashing Used?

You'll encounter it in systems involving:

- Distributed caches
- Distributed databases
- Key-value stores
- Load distribution
- Large-scale storage systems

The important system-design question is:

> **"How do I distribute keys across many servers while keeping the system stable when servers change?"**

Consistent hashing is one answer.

## 8. Programming / DSA Connection

Consistent hashing uses concepts such as:

**Hashing → Hash function → Key mapping → Searching for the next server**

A practical implementation commonly uses a **sorted structure** to find the next server on the ring efficiently.

## 9. The Most Important Difference

Remember this comparison:

| | Normal Hashing | Consistent Hashing |
|---|---|---|
| Formula | `hash(key) % N` | Hash ring lookup |
| Server count changes (e.g. `N = 3 → N = 4`) | Many keys may move | Only a limited portion of keys move |

## 10. One Important Advanced Problem

There is one problem with putting each server only **once** on the ring: the servers may become unevenly distributed.

## Revision Note

> **Consistent hashing = distributing data among servers using a hash ring, so that adding or removing a server causes only a small amount of data movement.**

**Memory trick:**
- **Normal hashing:** server changes → lots of data moves.
- **Consistent hashing:** server changes → little data moves.
