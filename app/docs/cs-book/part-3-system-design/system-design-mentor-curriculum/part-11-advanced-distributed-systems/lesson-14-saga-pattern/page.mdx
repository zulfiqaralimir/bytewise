# Lesson 14 — Saga Pattern

We now reach the second major approach to distributed transactions. In Lesson 13 we saw Two-Phase Commit, which can involve coordination, resource holding, and blocking when the coordinator fails. The **Saga Pattern** takes a different approach:

> **Break one large distributed transaction into a sequence of smaller local transactions, and use compensating transactions when something later fails.**

We cannot simply `BEGIN`, touch all four databases, and `COMMIT` — they're independent services. We need another strategy.

## 2–3. The Big Idea, and Compensation vs Rollback

Instead of one huge transaction, Saga creates a chain of local transactions, each committing on its own: `Create Order → Reserve Inventory → Charge Payment → Create Shipment`. If everything succeeds, we're done. If something fails, we **compensate** the previous steps — and compensation is not the same as rollback.

## 7. Each Step Needs a Compensation

| Action | Compensation |
|---|---|
| Create order | Cancel order |
| Reserve inventory | Release inventory |
| Charge payment | Refund payment |
| Reserve hotel | Cancel reservation |
| Book flight | Cancel booking |

For every Saga step, ask: *"if a later step fails, how do I compensate this step?"*

## 8. But Compensation Isn't Always Perfect

You can't "unsend" an email that already told the customer *"your order has shipped."* You could send a correction, but that's not the same thing. **Not every business operation has a perfect compensation** — this affects the order in which Saga steps should occur.

## 10. Two Ways to Coordinate a Saga

There are two major Saga styles: **choreography** and **orchestration**.

## 14. The Problem with Choreography

Three services (`A → B → C`) is easy to follow. But once a workflow grows to seven or more interacting services, each reacting to several possible events, the overall picture becomes genuinely hard to trace. As the number of participants grows, choreography can become harder to understand, debug, and maintain.

## 17. Choreography vs Orchestration

| | Choreography | Orchestration |
|---|---|---|
| Coordinator | No central orchestrator | Central orchestrator |
| Communication | Events | Commands/messages |
| Workflow | Distributed | Explicit in orchestrator |
| Coupling | More decentralized | More centralized |
| Visibility | Harder to see globally | Easier to see |
| Best fit | Smaller/simple flows | Complex/long workflows |

The core distinction is **who decides the next step.**

## 18. Saga vs 2PC

**2PC** coordinates participants toward one atomic commit decision, requiring unanimous YES before anyone commits.

## 19–20. The Fundamental Trade-off, and Saga Does NOT Give Global ACID

**2PC:** strong atomic commit, more coordination, potential blocking. **Saga:** independent local commits, compensation, temporary inconsistency possible. Between the inventory reservation succeeding and the compensation completing, the system may briefly be `Inventory = reserved, Payment = unpaid, Order = pending` — a genuinely inconsistent intermediate state. So:

> **Saga generally provides business-level eventual consistency, not the same global atomic isolation as a single ACID transaction.**

## 21. Saga and Eventual Consistency

This mirrors Lesson 10's chain (`Divergence → Propagation → Reconciliation → Convergence`): Saga goes through `Local commits → Temporary distributed state → Failure detected → Compensation → Desired final state`. Saga is closely related to the idea of eventual convergence of *business* state.

## 22–24. Saga, Idempotency, and Message Delivery

If a `Release Inventory` call succeeds but its response is lost, the orchestrator may retry it — and if the operation isn't safe to repeat, releasing the same items twice could corrupt inventory counts. Messages passing through a broker can also be delayed, duplicated, retried, or arrive out of order. So Saga steps and compensations should generally be designed with **safe retry/idempotency** in mind — this is one reason real Saga implementations become significantly more complicated than the happy-path diagram suggests.

## 25. A Critical Problem: Database + Message

If Inventory Service updates its database and then crashes before publishing `InventoryReserved`, the inventory is reserved but the next Saga step never happens. One common solution is the **Transactional Outbox** pattern: within the same local database transaction, update the business data *and* store the outgoing event; a separate process then reliably publishes the stored event. This avoids needing a distributed transaction between the database and the message broker.

## 26. Long-Running Transactions

A travel booking (`Flight → Hotel → Car → Insurance`) might take minutes; holding distributed locks the whole time is undesirable. Saga lets each booking commit independently and compensates only if something later fails — making it well suited to long-lived business workflows.

## 27. Real-World Examples

E-commerce (`Order → Inventory → Payment → Shipping`), travel (`Flight → Hotel → Car Rental`), banking (`Loan Application → Credit Check → Account Creation → Disbursement`), and food delivery (`Order → Restaurant Acceptance → Payment → Driver Assignment → Delivery`) all involve multiple services and failure points that fit the Saga model.

## 28. Saga Is Not Magic

Saga doesn't "solve" distributed transactions — it provides a strategy for managing distributed business workflows and recovering from partial failures through local transactions and compensation. You still need to handle network failures, retries, duplicate messages, timeouts, ordering, idempotency, partial failure, compensation failure, and observability. Complexity grows with the workflow.

## 29. What If Compensation Fails?

If `Refund Payment` itself fails after payment and inventory both succeeded but shipping didn't, you can't simply "roll back" — the payment was already committed. The compensation itself must usually be retried, tracked, idempotent, and recoverable, which is why production Saga systems need durable state and strong observability.

## 32. Choreography vs Eventual Spaghetti

A small choreography (`A → B → C`) is elegant. A large one, where each service reacts to several possible events from several other services, can leave you asking *"why did Service F do this?"* with an answer that traces through five indirect events. This is sometimes called **event-driven complexity**.

## 33. Why Orchestration Can Help

With an explicit orchestrator, you can inspect one place and see the whole flow: create order, reserve inventory, charge payment, create shipping, and what to compensate on failure. This can make complex workflows easier to reason about and monitor — at the cost of a central coordination component that concentrates the workflow logic.

## 34. The Most Important Comparison in Part 11

| Concept | Main Question |
|---|---|
| Distributed Transaction | How do multiple systems participate in one business operation? |
| 2PC | Can all participants atomically commit or abort together? |
| Saga | How can we complete/recover a multi-service workflow using local transactions and compensation? |
| Distributed Lock | Who owns a resource right now? |
| Consensus | What should distributed nodes agree on? |
| Replication | How do we maintain multiple copies? |
| Conflict Resolution | What do we do when concurrent updates conflict? |

Distributed Transactions sit at the bottom of that chain, splitting into **2PC** and **Saga**.

## 36. The Four Golden Memories

**2PC** — `Prepare → Vote → Commit/Abort`, `ALL YES → COMMIT`, `ANY NO → ABORT`.

**Saga** — `Local Transactions → Compensation`, `T1 → T2 → T3 → FAILURE → C2 → C1`.

**Choreography** — events tell services what happens next: `A → event → B → event → C`.

**Orchestration** — a central orchestrator tells services what to do.

## 37. The Most Important Interview Question

**"Explain Saga vs 2PC."**

> Two-Phase Commit coordinates multiple participants toward an atomic commit or abort decision. Saga instead decomposes a distributed business transaction into a sequence of local transactions and uses compensating transactions when later steps fail. 2PC provides stronger atomicity but can introduce coordination and blocking concerns, while Saga accepts temporary inconsistency and requires application-level compensation.

## 38. Common Mistakes

**Mistake — "Saga is rollback."** No — rollback ≠ compensation.

**Mistake — "Saga guarantees ACID."** No — Saga generally sacrifices global atomicity/isolation in favor of independently committed steps and business-level recovery.

**Mistake — "Choreography has no communication."** Wrong — it has lots of communication, usually through events.

**Mistake — "Orchestration means one database."** No — the orchestrator coordinates multiple independent services.

**Mistake — "Compensation always perfectly reverses an action."** No — some real-world effects cannot be perfectly undone.

**Mistake — "Saga eliminates failures."** No — it gives you a structured way to handle failures.

## 39. Final Memory Formula

```text
2PC:   PREPARE → VOTE → COMMIT/ABORT
SAGA:  LOCAL COMMIT → LOCAL COMMIT → FAILURE → COMPENSATE
CHOREOGRAPHY:  EVENT → SERVICE → EVENT → SERVICE
ORCHESTRATION: ORCHESTRATOR → COMMAND → COMMAND → COMMAND
```

And the deepest idea:

> **2PC tries to make multiple systems behave like one atomic transaction. Saga accepts that they are separate systems and coordinates their business actions and compensations instead.**
