# Lesson 13 — Two-Phase Commit (2PC)

We have reached the first major solution to the distributed transaction problem from Lesson 12. We want: **either everybody commits, or everybody aborts.** Two-Phase Commit, or **2PC**, is a protocol designed to coordinate exactly this kind of atomic commit across multiple transaction participants.

## 1. What Is 2PC?

**Two-Phase Commit is a distributed transaction protocol in which a coordinator asks all participants to prepare first, and then tells them all to either commit or abort.** The two phases are `Phase 1 → PREPARE / VOTE` and `Phase 2 → COMMIT / ABORT`. The key rule: `ALL YES → COMMIT`, `ANY NO → ABORT`.

> **2PC requires unanimity, not majority.** This is different from Raft and Paxos.

## 2. The Main Players

The **coordinator** manages the distributed transaction — *"I will ask everyone whether they are ready, then announce the final decision."* The **participants** are the databases/services that actually perform parts of the transaction.

## 3. Real-Life Analogy

Three people are buying a house together. Before signing, the coordinator asks each *"are you ready?"* If everyone says yes, everyone signs. If even one says no, nobody signs. That's the basic idea of 2PC.

## 4. Example: Online Order

A laptop purchase needs `create order`, `reserve laptop`, `charge customer`. We want all three to succeed or all three to fail — never a state where order and inventory succeed but payment fails.

Each participant records enough durable information to survive a crash before responding YES — this is a durable promise that it can complete the transaction if the coordinator later says commit.

## 6. What Does "Prepared" Actually Mean?

**Prepared does NOT mean committed.** It means *"I have done the necessary work and recorded enough information that I can commit later if instructed."* A participant may have performed local checks, recorded transaction information durably, and acquired necessary locks/resources — but it has **not yet made the final commit decision.**

## 7–8. Phase 1 Responses and What If One Says NO

If Order, Inventory, and Payment all vote YES, the coordinator proceeds to Phase 2. But if Inventory votes NO (say, the laptop is unavailable), the rule is `ANY NO → ABORT`, and the coordinator tells every participant to abort.

## 9. Phase 2 — COMMIT

If everyone said YES, the coordinator makes the final decision and broadcasts `COMMIT` to every participant, which then commits its local transaction.

**Memory rule:** `Prepare → Vote → Decide → Commit/Abort`

## 11–12. The Most Important Rule

`ALL participants = YES → COMMIT`, but `ANY participant = NO → ABORT`. Unlike Raft's *"majority can make progress,"* 2PC needs **everyone** to agree. With three participants `A, B, C`, even `A=YES, B=YES, C=NO` cannot commit as "2 out of 3" — C is part of the transaction, and letting A and B commit while C aborts is exactly the partial-commit problem 2PC exists to prevent.

## 13. 2PC vs Raft

| | Raft | 2PC |
|---|---|---|
| Question | What should the replicated cluster agree on? | Can every participant commit this transaction? |
| Requirement | Majority / quorum (e.g. 3/5) | Unanimous — all participants YES |
| Goal | Consensus / replicated state machine | Atomic commit across resources |

Don't confuse them.

They can't safely commit (the coordinator might have decided abort) and can't safely abort (it might have decided commit) — this **blocking behavior** is one of the major limitations of classic 2PC.

## 16. Why Do Participants Hold Locks?

If Inventory releases its reservation on `Laptop #123` immediately after preparing, another transaction could grab it — then the coordinator says COMMIT and the original transaction can no longer safely complete as intended. So participants hold resources/locks while prepared, which means a slow or unavailable coordinator makes other transactions wait too, hurting latency and availability.

## 17–19. Failure Scenario and Durable Logs

If the coordinator decides COMMIT and then crashes before every participant hears it, you can end up with `A → maybe committed, B → prepared, C → prepared`. The system must use durable logs to recover consistently — both participants (*"I had prepared transaction T"*) and the coordinator (*"T123 → COMMIT"*) need to survive a crash and resume from where they left off. This durability requirement is a major reason 2PC is more complicated than simply sending messages back and forth.

## 21–22. 2PC Is Not "Two Servers" or "Two Transactions"

"Two-phase" refers to **two protocol phases** (prepare, then commit/abort) — not two servers. You could have one coordinator and three participants, or one coordinator and twenty. Likewise, there aren't literally "two transactions" — several local transactions participate in **one** distributed transaction, and the phases are coordination stages around that single logical operation.

## 23. 2PC and ACID

2PC is particularly related to **Atomicity** across multiple resource managers. Without coordination you could get `DB-A → COMMIT, DB-B → ABORT`; with 2PC, the distributed transaction is given an atomic commit/abort outcome across participating resources, assuming the protocol's required assumptions and recovery mechanisms hold.

## 24. 2PC vs Saga

**2PC:** `Prepare → Everyone ready? → Commit together` — strong atomic commit across transaction-aware participants.

**Saga:** `Local transaction → Local transaction → Failure → Compensating transactions` — business-level recovery without keeping one global atomic transaction open.

> **2PC = "Everyone commit together." Saga = "Commit locally, compensate if necessary."**

## 25–26. When Is 2PC Useful — and Why Microservices Often Prefer Sagas

2PC makes sense when participants support distributed transactions, atomicity is genuinely required, resources are under controlled infrastructure, and partial commit is unacceptable — think controlled enterprise databases behind a transaction manager. But it's expensive: coordination, network round trips, durable logging, held locks, blocking, and coordinator dependency all add cost. Can you force an external payment gateway or courier API to participate in your 2PC protocol, holding a prepared state until you say commit? Usually not — which is why systems spanning external services tend toward the Saga model: charge payment, and if something later fails, refund it.

## 27. The Deep Connection to Consensus

Both **Consensus** (*"what value/decision should the distributed system agree on?"*) and **2PC** (*"can all participants commit this transaction, and then carry out the same commit/abort decision?"*) involve distributed nodes reaching agreement — but 2PC's classic coordinator-based design has a blocking weakness that consensus algorithms such as Raft are designed differently around.

## 28. The 2PC Memory Formula

> **PREPARE → VOTE → DECIDE → COMMIT/ABORT**

```text
ALL YES → COMMIT
ANY NO  → ABORT
```

And the weakness: coordinator failure → participants may block → locks/resources may remain held.

## 29. Interview Questions

**Q1. What is Two-Phase Commit?**
> A distributed atomic-commit protocol that coordinates multiple transaction participants so they either all commit or all abort.

**Q2. What are the two phases?**
> Prepare/Voting, then Commit/Abort.

**Q3. What happens if one participant votes NO?**
> Any NO leads to an abort for everyone.

**Q4. Does 2PC use majority voting?**
> No — a successful commit requires all participants to vote YES.

**Q5. What happens if the coordinator fails?**
> Prepared participants may be unable to determine the final decision and can become blocked until recovery/decision information becomes available.

**Q6. Why are logs necessary?**
> To make transaction state and decisions durable across crashes and allow recovery.

**Q7. Why can 2PC hurt performance?**
> It requires coordination, network communication, durable logging, and may keep locks/resources held while waiting for the final decision.

**Q8. Is 2PC the same as Raft?**
> No — Raft is consensus/replicated state machine; 2PC is distributed atomic commit.

**Q9. Is 2PC the same as Saga?**
> No — 2PC is atomic commit/abort; Saga is local transactions plus compensation.

## Final Mental Model

If you remember only five things: **(1)** coordinator + participants, **(2)** Phase 1: PREPARE → YES/NO, **(3)** Phase 2: COMMIT/ABORT, **(4)** ALL YES → COMMIT, ANY NO → ABORT, **(5)** coordinator failure → possible blocking.

**One-line exam definition:**

> **Two-Phase Commit (2PC) is a distributed transaction protocol in which a coordinator first prepares and collects votes from all participants, then instructs all participants to either commit or abort based on the unanimous result.**
