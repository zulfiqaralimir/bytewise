# Lesson 4 — Raft Consensus Algorithm

Now that we understand **what consensus is**, we can learn one of the most important practical consensus algorithms:

> **Raft**

Raft is designed to help a group of distributed servers <span style={{ color: "#0d9488", fontWeight: 700 }}>agree on an ordered sequence of commands</span>, <span style={{ color: "#dc2626", fontWeight: 700 }}>even when some servers fail</span>.

## 1. Why Do We Need Raft?

From Lesson 3, we learned:

> **Consensus = distributed nodes agreeing on a common decision/state.**

Now imagine three servers — `A`, `B`, `C` — all maintaining a copy of the same database. A client sends `SET X = 50`. We want:

| Node | Value |
|---|---|
| A | X = 50 |
| B | X = 50 |
| C | X = 50 |

and, importantly, we want them to agree on **the same order of commands**. <span style={{ color: "#0d9488", fontWeight: 700 }}>Raft provides a structured way to achieve this.</span>

## 2. The Big Idea Behind Raft

Raft makes the distributed system easier to understand by giving nodes different roles. There are **three roles**: <span style={{ color: "#0d9488", fontWeight: 700 }}>Leader</span>, <span style={{ color: "#475569", fontWeight: 700 }}>Follower</span>, and <span style={{ color: "#b45309", fontWeight: 700 }}>Candidate</span>.

## 4. Why Does Raft Need a Leader?

Imagine five nodes all independently accepting commands:

```text
A → command X
B → command Y
C → command Z
```

Now we have a difficult question: **in what order should these commands appear?** Raft simplifies the problem by having one leader coordinate the ordering.

## 5. Raft Uses a Log

This is one of the most important ideas. A Raft node maintains a **log** — an ordered sequence of commands.

| Index | Command |
|---|---|
| 1 | SET X = 10 |
| 2 | SET X = 20 |
| 3 | SET Y = 50 |
| 4 | DELETE Z |

## 6. Why Does Order Matter?

Suppose the commands are `SET X = 10` followed by `SET X = 20`. If they happen in that order, the final state is `X = 20`. But if they happen in the opposite order, the final state is `X = 10`.

Therefore:

> **Distributed systems often need agreement not only on WHAT commands happened, but also on their ORDER.**

Raft's replicated log helps solve this.

## 12. What Is a Term?

Raft divides time into logical periods called **terms**. Think of a term as an election era.

| Term | Leader |
|---|---|
| 1 | Leader A |
| 2 | Leader B |
| 3 | Leader C |

Each term has an integer identifier: `1, 2, 3, 4, ...`. A term helps nodes determine which leadership information is newer. For example, if Node A knows `term = 5` and Node B says `term = 4`, A can recognize that B's information is from an older term. This helps prevent confusion between old and new leaders.

## 15. Majority and Quorum in Raft

Suppose we have three nodes, `A`, `B`, `C`. A majority is:

```text
2 / 3
```

Suppose A is leader, and:

```text
A ✓
B ✓
C ❌
```

There are still `2 / 3`, so the cluster may continue making progress, assuming the necessary protocol conditions are satisfied. But if:

```text
A ❌
B ❌
C ✓
```

only one node remains — `1 / 3`, no majority. The cluster cannot safely continue committing new entries. This is a key Raft principle:

> **Without a quorum, Raft sacrifices progress rather than allowing conflicting decisions to be committed.**

- **Counters** — term, vote count, log index

- **Networking** — `send()`, `receive()`
- **State Machine** — command → state transition

> **Raft is not just a theoretical algorithm. It combines data structures, networking, state machines, persistence, and failure handling.**

## 24. The Most Important Raft Terms

| Term | Simple Meaning |
|---|---|
| **Leader** | Coordinates replication and normally handles client commands |
| **Follower** | Receives replicated information and follows the leader |
| **Candidate** | Node seeking leadership |
| **Term** | Logical period associated with leadership/elections |
| **Log** | Ordered sequence of commands |
| **Heartbeat** | Leader message indicating it is still active |
| **Election timeout** | Timeout after which a follower may start an election |
| **Vote** | A node's election choice |
| **Quorum** | Required participation, often a majority |
| **Commit** | Entry is considered safely agreed according to Raft's rules |
| **State machine** | Applies committed commands to produce application state |

## 25. Common Mistakes

**Mistake 1 — "The leader stores all the data."** Not necessarily. The leader coordinates replication; followers can maintain replicated copies.

**Mistake 2 — "If the leader fails, any follower becomes leader immediately."** No. An election must occur and the candidate must obtain the required votes.

**Mistake 3 — "Heartbeat proves the leader is alive."** Not exactly. It means the follower is receiving communication from the leader. A network problem can make a healthy node appear unreachable.

**Mistake 4 — "Replication is Raft."** No. Raft is a consensus algorithm that uses replicated logs to achieve agreement.

**Mistake 5 — "Raft guarantees availability even if most nodes fail."** No. If the cluster loses its quorum, it cannot safely commit new entries.

## 26. Interview Questions

**Q1. What is Raft?**
> Raft is a distributed consensus algorithm that helps a cluster of nodes agree on an ordered replicated log, using leader election and quorum-based replication.

**Q2. What are the three Raft states?**
> Leader, Follower, and Candidate.

**Q3. Why does Raft use a leader?**
> The leader simplifies coordination by being responsible for ordering and replicating client commands.

**Q4. What happens when the leader fails?**
> Followers eventually time out, a candidate starts an election, and a node that receives a majority of votes becomes the new leader.

**Q5. What is a Raft log?**
> An ordered sequence of commands that the cluster replicates across nodes.

**Q6. What is a quorum?**
> The minimum required participation, commonly a majority, for the protocol to safely make progress or commit decisions.

**Q7. Why can't a minority partition continue committing entries?**
> Because it lacks a quorum, and allowing it to commit independently could create conflicting histories.
