# Lesson 7 — Distributed Locks

We now move from **Leader Election** to **Distributed Locks**. This lesson is important because distributed locks combine several ideas we have already learned:

> **Leader Election + Consensus + Leases + Failure Handling**

## 1. What Is a Distributed Lock?

A **distributed lock** is a mechanism that ensures that **only one process/node at a time can access or modify a particular shared resource** across a distributed system.

> **A distributed lock coordinates exclusive access to a shared resource among multiple computers or processes.**

Imagine two application servers both receive the job *"Generate the monthly financial report."* If both execute it simultaneously, you get conflicting, duplicated work.

## 3. Real-Life Analogy

Imagine a meeting room with only one key. Alice gets the key and enters; Bob waits. When Alice returns the key, Bob gets it. The key represents the lock. In distributed computing, the "key" is maintained by some coordination mechanism rather than physically sitting in someone's hand.

## 5. What Does "Lock Ownership" Mean?

Suppose the resource is `payment:12345`. Client A successfully acquires its lock, so `Owner = A`. Client B asks *"Can I acquire payment:12345?"* and the lock service says no — A currently owns it, so A works while B waits. After A releases, `Owner = B`.

## 6. Distributed Lock ≠ Database Transaction

These concepts are related but different. A **distributed lock** answers *"who is allowed to work on this resource right now?"* A **database transaction** answers *"how do I perform a group of database operations atomically and consistently?"*

```text
Lock:
    "Only one worker processes Order #100."

Transaction:
    UPDATE orders
    UPDATE payments
    INSERT audit_record

    COMMIT
```

A transaction doesn't automatically solve every distributed coordination problem. Likewise, a lock isn't a replacement for transaction semantics.

## 10. Lease vs Lock

An ordinary conceptual lock is `Acquire → Owner → Release`. A lease is `Acquire → Owner → Valid until T → Renew → Valid until T'`. If renewal stops, the lease expires and ownership ends.

> **Lock = ownership.**
> **Lease = time-limited ownership.**

## 11. But There Is a Dangerous Problem

Suppose Client A acquires the lock and starts working, then becomes paused — maybe a garbage-collection pause, CPU starvation, a suspended VM, or a temporary network failure. The lock service doesn't hear from A, so its lease expires, and Client B acquires the lock. Now A eventually wakes up still believing it holds the lock, and tries to write to the database — but B is now the legitimate owner.

## 13. How Fencing Solves the Stale Client Problem

A acquires the lock with `token = 41`, then pauses. The lease expires. B acquires with `token = 42` and writes to the database, which now remembers `highest token = 42`. When A wakes up and writes with `token = 41`, the database checks `41 < 42` and rejects it.

## 16. Safety vs Liveness

**Safety** — *something bad must never happen.* For a lock: two valid owners must not simultaneously perform protected operations.

**Liveness** — *something good should eventually happen.* For a lock: if the current owner crashes, another client should eventually be able to acquire the lock.

Leases primarily help with liveness, while fencing helps protect correctness against stale owners.

## 17. Common Implementations

Distributed locks can be implemented using different coordination/storage systems.

**Database** — a locks table can coordinate acquisition through a transaction or unique constraint:

| resource_id | owner | token |
|---|---|---|
| job-123 | A | 41 |

**Redis-style systems** — a common pattern uses an atomic "set if not exists" operation with an expiration:

```text
SET lock:job123 owner=A NX PX=10000
```

Meaning roughly: set the lock only if it doesn't exist, and give it a limited lifetime. But correctness-sensitive distributed locking has subtle failure cases, so simply putting a TTL on a key is not the same thing as having a fully safe locking design.

**ZooKeeper / etcd / Consul-style coordination** — dedicated coordination systems can provide primitives for locks, leases, leader election, sessions, and coordination. Consensus-backed coordination is especially useful when the lock state itself needs a strongly consistent authority.

## 20. Distributed Lock vs Replication

**Replication** creates multiple copies of data across nodes. **Distributed Lock** controls ownership — only one node may operate while the others wait. Replication does not automatically provide mutual exclusion.

## 21. Real-World Examples

Distributed locks are useful when we want **one worker to perform a particular action**.

**Scheduled job** — three servers run the same application. Without a lock, all three run *"daily cleanup"* at once. With a distributed lock, one server gets the lock and runs cleanup while the others wait.

**Database migration** — you don't want three servers running a migration simultaneously. A lock ensures one server performs the migration, then releases it.

**Singleton worker** — suppose only one server should refresh an expensive cache. A cache-refresh lock ensures only one of A, B, or C actually does the refresh.

## 25. Common Mistakes

**Mistake 1 — "I used a mutex, so my distributed system is protected."** No. A process-local mutex does not coordinate another machine.

**Mistake 2 — "I added a TTL, so the lock is completely safe."** Not necessarily. TTL/lease expiration helps recovery, but a stale client can still wake up and attempt an operation.

**Mistake 3 — "The lock service knows A lost the lock, so A can't do anything."** Not automatically. The stale client may still execute code.

**Mistake 4 — "Replication makes the lock safe."** No. Replication gives copies. Coordination determines ownership.

**Mistake 5 — "Leader election and distributed locking are the same."** No — leader election chooses a coordinator; a distributed lock gives exclusive ownership of a resource.

## 26. Interview Questions

**Q1. What is a distributed lock?**
> A mechanism that provides coordinated exclusive access to a shared resource across multiple processes or machines.

**Q2. Why isn't a normal mutex enough?**
> Because a normal mutex generally protects shared state within one process/machine and cannot coordinate independent machines.

**Q3. What is a lease?**
> A time-limited lock that expires if it is not renewed.

**Q4. Why use leases?**
> To prevent a crashed lock holder from holding the resource forever.

**Q5. What is a fencing token?**
> A monotonically increasing value issued with lock ownership so the protected resource can reject stale owners.

**Q6. Why isn't a lease alone enough?**
> A client can pause, lose its lease, and later resume believing it still has authority.

**Q7. What is the difference between safety and liveness?**
> Safety means bad things never happen; liveness means good things eventually happen.

**Q8. How can consensus help distributed locking?**
> A consensus-backed coordination service can maintain a consistent authoritative lock state across failures.

**Ultimate memory trick:**

> **DHT = WHERE?**
> **Routing = HOW do I get there?**
> **Replication = HOW MANY copies?**
> **Consensus = WHAT do we agree on?**
> **Leader Election = WHO coordinates?**
> **Distributed Lock = WHO owns the resource?**
> **Lease = FOR HOW LONG?**
> **Fencing Token = WHICH owner is newer?**

**One-line memory:**

> **Lock = one owner. Lease = temporary owner. Fencing token = stale owner cannot act.**

That last concept — **fencing tokens** — is one of the most important ideas to retain from this lesson.
