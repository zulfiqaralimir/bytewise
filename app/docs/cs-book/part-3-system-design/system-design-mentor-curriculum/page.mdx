# System Design Mentor Curriculum

**From Beginner → Advanced → Expert**

This is the master roadmap for learning System Design as a *chain*, not a pile of disconnected buzzwords:

> **Programming + DSA → Components → Architecture → Distributed Systems → Large-Scale System Design**

The goal isn't to memorize architecture diagrams for Netflix or Uber. It's to be able to look at any large-scale system and answer: why does this component exist, what problem does it solve, what's the programming and DSA happening inside it, how do the databases and networking work, how does it scale, how does it stay available, what happens when something fails, and what trade-off did the architect accept to get there.

Everything below is taught **one concept at a time** — never all at once. Each part builds on the last, and DSA is introduced exactly when a System Design topic needs it, not before.

## Part 1 — Programming & DSA Foundation

Before any System Design concept that leans on programming or DSA, the foundation gets taught first.

**Programming:**
- Functions, Classes and Objects, APIs
- HTTP/HTTPS, JSON
- Concurrency, Multithreading, Processes
- Networking basics
- Error handling
- Async/await, Synchronous vs Asynchronous programming

**Data Structures:**
- Arrays, Strings, Linked Lists
- Stacks, Queues
- Hash Tables, Sets
- Trees, Heaps, Graphs

**Algorithms:**
- Searching, Sorting, Binary Search
- Recursion, BFS, DFS
- Greedy algorithms, Dynamic Programming
- Hashing, Graph algorithms
- Time Complexity, Space Complexity

Every DSA concept gets tied explicitly to **"Where is this used in System Design?"** — for example:

- **Hash Table** → Caching → Database indexing → Consistent hashing → Distributed systems
- **Queue** → Message queues → Asynchronous processing → Event-driven architecture
- **Heap** → Priority queues → Task scheduling → Distributed job systems
- **Graph** → Network relationships → Service dependencies → Routing

## Part 4 — Database System Design

**Database Fundamentals:**
- SQL, NoSQL
- Relational databases
- Document databases
- Key-value databases
- Column databases
- Graph databases

**Advanced Database Design:**
- Indexing, Transactions, ACID, Isolation levels
- Replication, Primary/Replica architecture, Read replicas
- Partitioning, Sharding, Database federation
- Distributed databases

The three terms that get confused most often are always kept distinct:

| Term | Meaning |
|---|---|
| **Replication** | Copying data — the same data lives on multiple servers |
| **Partitioning** | Dividing data — splitting one dataset into smaller pieces |
| **Sharding** | Distributing partitions across different database servers |

Each one is taught with exactly when it should be used, not just what it is.

**Every system follows the same ten-step process:**

| Step | What Happens |
|---|---|
| 1. Requirements | Functional + non-functional requirements |
| 2. Scale | Estimate users, requests/sec, storage, bandwidth, read/write ratio |
| 3. High-Level Architecture | `User → API → Services → Cache → Database`, refined toward production-grade |
| 4. Choose Components | Justify load balancer, cache, database, replicas, shards, queue, CDN, API gateway, microservices |
| 5. Data Model | The important tables/documents |
| 6. APIs | The important endpoints |
| 7. Scaling | How the design holds up from 10 users → 10,000 → 1M → 100M |
| 8. Failure Scenarios | "What happens if this component fails?" |
| 9. Trade-offs | Why this architecture over the alternatives |
| 10. DSA & Programming Connection | Explicit lists: DSA used, programming concepts used, database concepts used, networking concepts used, distributed-system concepts used |

## The Concept Connection Map

Every concept learned gets threaded through the same running map:

> **DSA → Programming → Component → System Design → Real-World Application**

Two worked examples:

**Hash Table** → fast key-value lookup → cache implementation → distributed cache → used in Netflix/Instagram-type systems

**Queue** → FIFO data structure → producer/consumer programming → message queue → asynchronous processing → large-scale notification system

## Final Objective

By completing this curriculum, looking at a large-scale system should make it possible to understand:

- Why this component exists
- What problem it solves
- What programming is happening inside it
- What DSA is being used
- How databases are involved
- How networking is involved
- How the system scales
- How the system remains available and reliable
- What happens when something fails
- What trade-offs the architect made

> **Simple takeaway:** The goal is not to memorize architecture diagrams — it's to understand the full chain from programming and DSA up through distributed systems and large-scale architecture, well enough to reconstruct any diagram from first principles.
