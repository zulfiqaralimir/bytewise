# Algorithms by Abdul Bari

## 1.3: How to Write and Analyze an Algorithm

*Based on [Abdul Bari's Algorithms playlist](https://youtu.be/0IAPZzGSbME?si=yLoAVtKfYvm_5b8K).*

---

## How to Write an Algorithm

[Section 1](/docs/cs-book/part-2-algorithms/algorithms-by-abdul-bari/chapter-1/1-introduction-to-algorithms) already drew the line: an **algorithm** is a step-by-step procedure for solving a problem — it is *not* a program. That distinction matters more than it first appears once you sit down to actually write one.

- A **program** is written in a specific language and must follow that language's exact syntax — every variable needs a declared **data type**, and nothing can be used before it's declared.
- An **algorithm** skips all of that. You don't decide data types, you don't formally declare variables, and there is **no fixed syntax** to follow.

**Why the flexibility exists:** an algorithm is meant to communicate a solution clearly to anyone working on the project — not to satisfy a compiler. As long as the people implementing or reviewing it can follow the logic, the notation you choose is up to you.

### Example: swapping two values

Because there's no fixed syntax, the same algorithm can be written in more than one acceptable style. Both of these communicate exactly the same procedure:

**Style A — brace block, simple assignment**

```
Algorithm Swap(a, b)
{
    temp = a;
    a = b;
    b = temp;
}
```

**Style B — Begin/End block, arrow assignment**

```
Algorithm Swap(a, b)
Begin
    temp ← a;
    a ← b;
    b ← temp;
end
```

The arrow symbol (←) for assignment is borrowed from languages like Pascal. Some writers use `=`, some use `←` — both communicate "store this value here," and either is acceptable as long as it's used consistently and clearly.

**Think of it like** handwriting a recipe for a friend versus filing it with a food-safety regulator: the friend just needs to follow the steps, so any clear notation works. There's no inspector checking your syntax against a spec.

**Key takeaway:** there is no single correct way to write an algorithm. Consistency and clarity for your intended audience matter more than matching any particular notation.

## Criteria for Analyzing an Algorithm

Once an algorithm is written, it needs to be evaluated — not just for correctness, but for *efficiency*. Two criteria are analyzed almost universally:

1. **Time** — how long the procedure takes to produce a result. A slow, lengthy procedure is worse than a fast one that reaches the same answer.
2. **Space** — how much memory the procedure will consume once it actually runs as a program on a machine.

Beyond these two, additional criteria become relevant depending on the context of the application:

- **Network / data transfer** — for internet-based or cloud-based applications, how much data the procedure moves matters. Unnecessarily transferring large or uncompressed data is a real cost.
- **Power consumption** — increasingly relevant since most computing now happens on handheld and portable devices (phones, tablets, laptops) rather than only desktops.
- **CPU registers** — relevant specifically when writing low-level algorithms such as device drivers or system-level code, where the number of registers consumed becomes a genuine constraint.

**Which criteria apply depends entirely on your project.** Time and space are analyzed by default; the rest are pulled in as the situation demands.

---

## Time Complexity — Worked Example

The rule at this level of analysis: **every simple, direct (non-nested) statement counts as one unit of time**, regardless of how complex that statement's underlying operations might be once compiled. This is a deliberately shallow level of analysis — you *could* go deeper (down to generated machine code, where a single multiplication might expand into several machine instructions), but for algorithm design purposes, one statement = one unit of time is the standard convention.

Applying this to the swap algorithm:

| Statement | Time |
|---|---|
| `temp = a;` | 1 |
| `a = b;` | 1 |
| `b = temp;` | 1 |
| **Total: f(n)** | **3** |

The result, **f(n) = 3**, is a **constant** — it does not depend on any input size $n$. Whether a statement is simple (`temp = a;`) or more complex (e.g., `x = 5*a + 6*b;`), it's still counted as a single unit of time at this level of analysis, because the goal is to capture the *shape* of the algorithm's growth, not the exact machine-level cost.

**How much detail is "enough"?** That depends on the goal. A simple task doesn't need exhaustive planning; a task with much higher stakes and complexity justifies a much more careful, detailed analysis. The right depth of analysis scales with what the algorithm needs to accomplish.

---

## Space Complexity — Worked Example

Space complexity is analyzed the same way: **count the variables used**, and each variable is counted as consuming **one word** of memory (not bytes — at the algorithm level, we don't yet know whether a variable will become an `int`, `float`, or `double`, so "word" is used as a data-type-agnostic unit).

| Variable | Space |
|---|---|
| `a` | 1 |
| `b` | 1 |
| `temp` | 1 |
| **Total: S(n)** | **3 words** |

Like the time result, this is a fixed value that doesn't grow with input size.

---

## Expressing Constant Complexity: O(1)

When either the time function $f(n)$ or the space function $S(n)$ evaluates to a fixed value — regardless of what that value actually is — it is expressed using **Big-O notation as $O(1)$**.

- $f(n) = 3 \rightarrow O(1)$
- $S(n) = 3 \text{ words} \rightarrow O(1)$

This holds whether the constant is 3, 30, or 3000. $O(1)$ simply means "constant" — the resource usage does not scale with the size of the input at all.

---

## The Big Picture

- An algorithm is a language-agnostic problem-solving procedure with no fixed syntax — clarity for your audience is what matters.
- The two primary analysis criteria are **time** and **space**; **network usage**, **power consumption**, and **CPU registers** apply situationally.
- At this basic level of analysis, each simple statement = 1 unit of time, and each variable = 1 word of space.
- A constant result — independent of input size $n$ — is written as $O(1)$.
- This worked example is the launchpad for the next topic: asymptotic notation, where $f(n)$ stops being a plain number and starts being a function of $n$.

> **Simple takeaway:** writing an algorithm is about clarity, not syntax — but analyzing one is about counting statements and variables until you can name its growth, and a fixed count with no dependence on $n$ is always $O(1)$.
