# 11.1: Linked List — Introduction & Concepts

---

## 1. The Problem With Arrays

Before we can appreciate why linked lists exist, it helps to see exactly where arrays fall short.

**An array has a fixed size.** The moment you create one, you must state how many elements it can hold — and that number can never change afterward. This is the core problem, and here's why it matters in practice:

- As programmers, we write programs for *users* — and it's the user, not us, who decides how many elements they'll actually need to store.
- We don't know that number in advance. It's only determined at **runtime**, once the program is actually running.
- But an array's size has to be fixed at **compile time** (or at least at the moment of creation) — long before we know what the user will need.

This creates a lose-lose situation:

- **Declare it too small**, and once the user has more elements than that, there's simply nowhere to put them.
- **Declare it too large** "just to be safe," and most of that space sits wasted, unused, for the entire life of the program.

**Analogy:** think of an array like a bench with a fixed number of seats. The moment you build the bench, you commit to its capacity. If five people show up but the bench only seats three, two people are left standing. If only two people show up to a ten-seat bench, eight seats sit empty. Either way, the fixed size works against you.

## 2. A Quick Reminder: Arrays in Stack vs. Heap

We can create an array in two places:

- **On the stack:** e.g. `int A[5];` — this array lives inside the activation record of the function that declared it.
- **On the heap:** e.g. `int *P = new int[5];` — here, a pointer `P` lives on the stack, but it points to array memory that was dynamically allocated on the heap. The nice part is that the size can be decided at runtime and passed in.

Either way, though, once that array is created — whether on the stack or the heap — **its size is locked in**. Creating it on the heap lets you *choose* the size dynamically, but it still can't grow or shrink afterward.

**The one real benefit of arrays:** all their elements sit in **contiguous memory** — side by side. This is exactly what lets you jump straight to any element using an index (`A[0]`, `A[1]`, `A[2]`, …), with no need to walk through the array to find something. This is efficient, but it comes bundled with that same fixed-size limitation.

## 3. The Idea Behind a Linked List

What we actually want is a data structure that can **grow when the user adds elements** and **shrink when they remove elements** — a genuinely variable-size structure.

Here's the shift in thinking: instead of reserving one big fixed block of memory up front (like the array's bench), what if **each element brought its own small piece of memory** with it, only when it's actually needed?

Picture it like this: instead of a bench with a fixed number of seats, imagine an open room where anyone who wants to join **brings their own chair**. The first person sits down. When a second person arrives, the first person's chair "links" to the new person's chair. The third person's chair links from the second, and so on — forming a chain.

- Want to remove someone from the middle? Just take their chair away, and re-link the chair before them directly to the chair after them.
- Want to insert someone new in the middle? Create their chair, and re-link the chairs around them to route through the new one.

Nothing else in the chain has to move. Only the **links** change.

Each "chair" — one element's data, plus a link to the next element — is what we call a **node**. Put together, a chain of these nodes, allocated dynamically in the heap, is a **linked list**.

**One important note:** a linked list only makes sense when built inside the **heap**, never the stack. Since we're allocating memory for each node individually and dynamically, as elements are added or removed, this naturally requires heap allocation.

## 4. What Is a Linked List? — A Formal Definition

Now that we have the intuition, here's the precise definition:

> A **linked list** is a collection of nodes, where each node contains **data** and a **pointer to the next node**.

Let's ground this with a concrete example. Suppose we have four nodes holding the values `8`, `3`, `7`, and `12`, and each node sits at some memory address:

- The first node is at address **200**, holds data `8`, and its pointer holds `210` (the address of the next node).
- The node at address **210** holds data `3`, and its pointer holds `270`.
- The node at address **270** holds data `7`, and its pointer holds `300`.
- The node at address **300** holds data `12`, and since it's the last node, its pointer holds nothing (**null**).

There's also a special pointer, usually called **first** (or **head**), that points to the very first node in the list — here, that's address `200`. This pointer itself lives at some address too (say, `100`), but that detail rarely matters in practice.

## 5. Defining a Node — a Self-Referential Structure

To actually build this in code, we need to define what a node looks like. A node needs exactly two things:

1. **Data** — this can be an integer, float, double, or any other type you need.
2. **A pointer to the next node** — and here's the interesting part: since "the next node" is itself a node, this pointer must be of the **same type** as the structure we're currently defining.

In C (and C++, which supports the same `struct` syntax), this looks like:

```c
struct Node {
    int data;
    struct Node *next;
};
```

Notice that the structure contains a pointer to *its own type*. This is called a **self-referential structure**, and it's the defining trait that makes linked lists possible.

**A note on C++:** a `struct` in C++ behaves almost identically to a `class`, with one key difference — members of a `struct` are `public` by default, while members of a `class` are `private` by default. So in C++, you're free to define a node using either a `struct` or a `class`.

**Working out the size of a node:** suppose, for a given compiler, an `int` takes 2 bytes. In that same compiler, a pointer will also typically take 2 bytes (this scales together — if `int` takes 4 bytes, so does the pointer, in most common setups). That gives us a total node size of **2 + 2 = 4 bytes**.

## 6. Creating and Accessing a Node

**Creating a node in C:** since nodes live in the heap, we need a pointer and the `malloc` function:

```c
struct Node *P;
P = (struct Node *) malloc(sizeof(struct Node));
```

This is fairly verbose — we have to compute the byte size, request it from `malloc`, and then type-cast the result (since `malloc` returns a generic `void*`).

**Creating a node in C++:** this becomes much simpler with the `new` keyword:

```cpp
P = new Node;
```

This one line creates a new node in the heap and stores its address in `P` — no manual size calculation or type-casting required.

**Accessing a node's members:** once `P` points to a node, we access its fields using the arrow (`->`) operator, since `P` is a pointer to a structure:

```c
P->data = 10;   // store 10 in the node's data field
P->next = 0;    // 0 means the node doesn't point anywhere (null)
```

## 7. Three Essential Pointer Statements

Once you're working with multiple pointers in a linked list, a small set of statements come up constantly. Suppose we have two pointers, `P` and `Q`, and `P` is currently pointing at some node.

**Statement 1 — `Q = P;`**
This copies whatever address is stored in `P` into `Q`. Both pointers now point to the **exact same node**. Nothing about the list itself changes — we've just made a second pointer refer to the same place.

**Statement 2 — `Q = P->next;`**
This stores *the address that P's node points to* into `Q`. In other words, `Q` now points to the node **right after** `P`'s node. Importantly, `P` itself doesn't move — only `Q` changes.

**Statement 3 — `P = P->next;`**
This is subtly different, and it's the single most important statement for traversing a linked list. Here, `P`'s *own* next-address gets written back into `P` itself. This means **`P` moves forward** to the next node. This is exactly the statement you'd use in a loop to walk through an entire linked list, one node at a time.

## 8. Checking Whether a Pointer Is Null

When working with linked lists, you constantly need to check whether a pointer is actually pointing to a node, or pointing nowhere (null). There are a few equivalent ways to write each check.

**Checking if `P` points to nothing** (any of these three work identically):

```c
if (P == NULL)
if (P == 0)
if (!P)
```

**Checking if `P` does point to a valid node** (again, all equivalent):

```c
if (P != NULL)
if (P != 0)
if (P)
```

These all rely on a simple rule from C/C++: the value `0` is treated as `false`, and any non-zero value is treated as `true`. Since a null pointer holds the value `0` and a valid pointer holds some real (non-zero) address, checking "is `P` truthy" is the same as checking "does `P` point somewhere."

**One more useful check — is this the last node in the list?** If `P` points to a node, you can check whether there's anything *after* it:

```c
if (P->next == NULL)   // P is the last node in the list
if (P->next != NULL)   // there is at least one more node after P
```

These small conditions come up over and over again once we start writing real linked list operations — traversal, insertion, deletion — which is exactly what the next video builds on.

---

**Key takeaway:** a linked list solves the array's fixed-size problem by letting each element carry its own memory, connected purely through pointers rather than physical position. This flexibility costs us direct indexing (we can no longer jump straight to the *n*-th element — we have to follow the chain), but in exchange, we gain a structure that can grow and shrink freely, and that supports easy insertion and removal anywhere in the list.
