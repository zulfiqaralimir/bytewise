# 4: Principle of Optimality — Introduction to Dynamic Programming

*Course: Algorithms | Based on the lecture by Abdul Bari*

---

## 1. Where Dynamic Programming Fits

Dynamic Programming is another problem-solving strategy in this course, grouped together with the **Greedy Method**:

1. Greedy Method
2. Dynamic Programming — **Principle of Optimality**

Both of these strategies are typically used for **optimization problems** — this is what sets them apart from strategies like backtracking, which searches for *all* valid solutions rather than the single best one.

The idea underlying Dynamic Programming is called the **Principle of Optimality**: an optimal solution to a problem can be constructed from optimal solutions to its **subproblems**. Rather than solving the same subproblem again every time it's needed, Dynamic Programming **solves each subproblem once, stores the result, and reuses it.**

### 1.1 Where to Use What

A quick decision guide for picking between the two:

- **Reach for Greedy when:** each choice, once made, never needs to be reconsidered — committing early can't box you out of the optimal answer later. This only holds when the problem has the **greedy-choice property.**
- **Reach for Dynamic Programming when:** a choice made now *could* conflict with a better option later, so you need to compare full subproblem outcomes rather than commit blindly. This is needed when the problem has **overlapping subproblems** and **optimal substructure.**
- **Not sure which applies?** Try the greedy approach first and look for a counterexample — a case where the locally best choice provably leads to a worse final answer. If you find one, the problem needs Dynamic Programming instead.
- **See Section 5 below** for a fuller side-by-side comparison of how the two strategies differ.

### 1.2 How to Understand the Situation

When you're facing a new optimization problem and need to work out which strategy it calls for, ask these questions in order:

1. **Does an early choice ever come back to bite you?** Walk through a small example by hand. If committing to the best-looking option right now can *permanently rule out* a better final answer, greedy is unsafe — you need DP.
2. **Can you prove the greedy-choice property, or only assume it?** If you can argue that swapping any greedy pick for a different one never improves the final result (an "exchange argument"), greedy is provably safe. If you're just *hoping* it works, that's a warning sign — test it.
3. **Do smaller subproblems get asked for more than once, from different paths?** If the same subproblem (e.g., `fib(2)`, or "best value using the first `i` items with capacity `w`") gets requested repeatedly through different decision paths, that's the signature of **overlapping subproblems** — a strong signal for DP.
4. **Does an optimal answer decompose cleanly into optimal answers to smaller versions of itself?** If yes, the problem has **optimal substructure** — the precondition the Principle of Optimality depends on, and what makes DP applicable at all.
5. **Run a brute-force check on a tiny case.** For a handful of items or elements, compute the true optimal by hand or exhaustively, then compare it against what greedy produces. A single mismatch is proof greedy fails here — no further argument needed.

> **Simple rule:** if you can find *any* small case where the greedy pick isn't part of the true optimal solution, stop trying to make greedy work — that counterexample is your proof you need Dynamic Programming instead.

## 2. A Motivating Example: Fibonacci Numbers

The Fibonacci sequence is defined by a simple recurrence:

$$
fib(n) =
\begin{cases}
0 & n = 0 \\
1 & n = 1 \\
fib(n-2) + fib(n-1) & n > 1
\end{cases}
$$

This produces the familiar sequence:

| n | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| fib(n) | 0 | 1 | 1 | 2 | 3 | 5 | 8 | 13 |

The direct, naive translation of this recurrence into code is a simple recursive function:

```c
int fib(int n)
{
    if (n <= 1)
        return n;
    return fib(n - 2) + fib(n - 1);
}
```

---

## 3. The Problem: Exponential Recomputation

This recursive version works correctly — but it is **extremely inefficient.** To see why, look at the full call tree for `fib(5)`:

<Figure src="/images/fib-recursion-tree-full.svg" alt="Recursion tree for fib(5) showing exponential branching, with time recurrence T(n)=2T(n-1)+1 and complexity O(2^n)" width={1000} height={430} caption="Every call to fib(n) makes two further recursive calls, so the tree roughly doubles in size at each level." />

- The time taken satisfies the recurrence $T(n) = 2T(n-1) + 1$.
- Solving this recurrence gives $O(2^n)$ — **exponential** time, even though the answer itself grows only linearly with `n`.

Now look closely at the *labels* in that tree — several of them repeat:

<Figure src="/images/fib-recursion-tree-duplicates.svg" alt="Same recursion tree for fib(5) with repeated subproblems highlighted: fib(3) computed twice, fib(2) three times, fib(1) five times, fib(0) three times" width={1000} height={460} caption="The exact same subproblem is recomputed from scratch, over and over: fib(3) is solved twice, fib(2) three times, fib(1) five times, and fib(0) three times." />

> **The core insight:** the naive recursive solution isn't slow because the problem is hard — it's slow because it keeps **redoing work it has already done.** This wasted, repeated computation is exactly what Dynamic Programming is designed to eliminate.

---

## 4. The Fix: Store and Reuse (Memoization / Tabulation)

The fix is simple in principle: keep an array `F[]` to record the answer to each subproblem **the first time it's computed**, so that every later request for the same subproblem is answered instantly instead of being recomputed.

<Figure src="/images/fib-dp-table-before-after.svg" alt="Array F initialized to -1 (not computed) for indices 0-5, then filled bottom-up to 0,1,1,2,3,5, with F[5]=fib(5)=5 highlighted" width={820} height={200} caption="Before: every entry is a sentinel value (-1) meaning 'not yet computed.' After: each entry is filled exactly once, and later steps simply read the stored value instead of recomputing it." />

### 4.1 Bottom-Up Implementation

The cleanest way to apply this idea for Fibonacci is to build the table **bottom-up** — starting from the known base cases and working upward, rather than recursing downward:

```c
int fib(int n)
{
    if (n <= 1)
        return n;

    F[0] = 0;
    F[1] = 1;
    for (int i = 2; i <= n; i++)
        F[i] = F[i - 2] + F[i - 1];

    return F[n];
}
```

- Each `F[i]` is computed **exactly once**, using two already-known values — never by branching into fresh recursive calls.
- By the time the loop reaches `i = n`, `F[n]` is ready to return directly.

> This is the essence of the **Principle of Optimality** in action: `fib(n)`'s optimal (and only) value is built directly from the already-solved, stored values `fib(n-1)` and `fib(n-2)` — nothing is ever solved twice.

### 4.2 The Payoff

| Approach | How subproblems are handled | Time Complexity |
|---|---|---|
| **Naive recursion** | Every subproblem is recomputed from scratch, every time it's needed | $O(2^n)$ |
| **Dynamic Programming** | Each subproblem is solved once, stored, and reused | $O(n)$ |

---

## 5. Greedy Method vs. Dynamic Programming

Since these two strategies are introduced together, it's worth being precise about how they differ — both are used for optimization problems, but they arrive at a solution in very different ways.

| Aspect | Greedy Method | Dynamic Programming |
|---|---|---|
| **How a choice is made** | Makes the **locally best** choice at each step, and **never reconsiders** it | Considers **results from multiple subproblems** and combines them to build the overall solution |
| **Subproblems explored** | Only **one** path is ever followed — whatever looks best right now | **Multiple overlapping** subproblems are solved (once each) and their results are reused |
| **Optimality guarantee** | Gives an optimal answer **only when the problem has the greedy-choice property** — otherwise it can settle for a suboptimal answer | Guarantees an optimal answer whenever the problem satisfies the **Principle of Optimality** |
| **Speed** | Generally **faster** — one pass, no storing/reusing of subproblem results | Generally **slower** than greedy, but still far faster than naive recursion, thanks to storing and reusing subproblem results |

> **In short:** Greedy commits to one choice at each step and moves on, hoping local decisions add up to a global optimum. Dynamic Programming is more thorough — it works out the optimal answer to every relevant subproblem (storing each one only once) and combines them, which is why it can guarantee optimality in cases where greedy cannot.

---

## 6. Key Takeaways

- **Dynamic Programming**, like the Greedy Method, is generally used for **optimization problems.**
- It rests on the **Principle of Optimality**: an optimal solution is built from optimal solutions to its subproblems.
- A naive recursive solution (e.g., for Fibonacci) can be correct but still **exponentially slow**, because it recomputes the same subproblems repeatedly.
- Dynamic Programming fixes this by **storing each subproblem's result** (in an array or table) the first time it's computed, and **reusing** that stored result afterward — instead of recomputing it.
- For Fibonacci, this turns an **$O(2^n)$** naive recursive solution into an **$O(n)$** Dynamic Programming solution.
- Building the table from the base cases upward (as shown here) is called a **bottom-up** approach — one of the two standard ways to implement Dynamic Programming (the other being top-down recursion with stored results, known as **memoization**).

> **Note:** this Fibonacci recursion is not backtracking — it has no choices to try and no constraints to check, so there's nothing to prune. The wasted work here comes from solving the same subproblem repeatedly, which Dynamic Programming fixes.
