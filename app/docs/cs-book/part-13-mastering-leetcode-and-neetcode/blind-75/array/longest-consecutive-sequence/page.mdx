# Longest Consecutive Sequence

**LeetCode #128 · 🟡 Medium**

*Blind 75 Problem 30 of 75 · Array*

---

### Problem Statement

> Given an array of integers `nums`, return the length of the longest consecutive sequence of elements that can be formed.

A **consecutive sequence** is a sequence of elements in which each element is exactly `1` greater than the previous element. The elements do **not** have to be consecutive in the original array — only the *values* need to form an unbroken chain; their positions in the input don't matter.

You must write an algorithm that runs in **O(n) time**.

```python
# Example 1
Input: nums = [2, 20, 4, 10, 3, 4, 5]
Output: 4
# The longest consecutive sequence is [2, 3, 4, 5]
```

**Constraints:**
- `0 <= nums.length <= 10⁵`
- `-10⁹ <= nums[i] <= 10⁹`

---

### Hint

Sorting first, then walking through counting consecutive runs, works — but sorting always costs `O(n log n)`, and the problem demands `O(n)`. What data structure gives you an **instant** "does this number exist?" check, and how could that check tell you where a sequence *starts*, so you only ever count each number once?

### Complete Walkthrough

#### <span style={{ color: "#dc2626", fontWeight: 700 }}>Sorting Approach</span>

The natural first idea: sort the numbers, then walk through counting consecutive runs.

```python
def longestConsecutive(nums):
    if not nums:
        return 0
    nums = sorted(set(nums))
    longest = 1
    current = 1
    for i in range(1, len(nums)):
        if nums[i] == nums[i - 1] + 1:
            current += 1
            longest = max(longest, current)
        else:
            current = 1
    return longest
```

**Breaking it down:**
- `nums = sorted(set(nums))` — dedupe with a set, then sort what's left.
- `current` tracks the length of the run in progress; `longest` tracks the best run seen so far.
- Each step compares a number to the one right before it: if it's exactly `+1`, the run continues; otherwise a new run starts at `current = 1`.

**Time Complexity: O(n log n)** — sorting `n` items always costs this, no way around it.

**Space Complexity: O(n)** — the deduped, sorted copy.

**Why it fails:** this is correct and would be a perfectly reasonable first pass in an interview, but the problem explicitly requires **O(n)**, and sorting can never be faster than `O(n log n)`. The real challenge is finding an approach that detects consecutive runs **without sorting at all**.

---

#### Intuition

Use a **set** — not a full dictionary, since all that's needed is an instant "does this exist?" check, not stored values.

For every number, ask one question: **is this number the *start* of a consecutive sequence?** A number is a sequence-start only if `number - 1` does **not** exist in the set. If `number - 1` *does* exist, this number is the middle (or end) of a sequence that starts earlier — not a start itself.

Only for true sequence-starts, count upward: check if `number + 1` exists, then `number + 2`, and so on, tracking how far the chain extends.

It might look like checking `+1, +2, +3...` for every number could be slow — but counting upward only ever happens from true sequence-starts. Every other number gets skipped with a single `O(1)` check. Since each number only ever gets "walked" once, as part of the one sequence it truly belongs to, the total work across the entire list still adds up to `O(n)`.

---

#### <span style={{ color: "#16a34a", fontWeight: 700 }}>Optimized Approach — Hash Set</span>

1. Drop every number into a set → instant `O(1)` existence checks, no sorting needed.
2. For each number, check if it's a sequence-start: is `number - 1` missing from the set?
3. If it is a start, count upward — `number + 1`, `number + 2`, ... — for as long as each next value exists in the set.
4. Track the longest chain found across all sequence-starts.

```python
def longestConsecutive(nums):
    num_set = set(nums)
    longest = 0

    for n in num_set:
        if n - 1 not in num_set:
            length = 1
            while n + length in num_set:
                length += 1
            longest = max(longest, length)

    return longest
```

**Breaking it down:**
- `num_set = set(nums)` — converts the list into a set, removing duplicates and enabling `O(1)` existence checks.
- `longest = 0` — tracks the best sequence length found so far.
- `for n in num_set:` — walk through every unique number; order doesn't matter here.
- `if n - 1 not in num_set:` — the sequence-start check: if the number just before `n` doesn't exist, `n` is where a sequence begins.
- `length = 1` — a sequence-start counts as length `1` by itself, before extending further.
- `while n + length in num_set:` — keep checking upward (`n+1`, `n+2`, `n+3`...) for as long as the next number in the chain exists.
- `length += 1` — extend the count each time the next number in the chain is found.
- `longest = max(longest, length)` — once the chain breaks, compare this chain's length against the best found so far.

**Trace it**, using `nums = [2, 20, 4, 10, 3, 4, 5]`:

```
num_set = {2, 3, 4, 5, 10, 20}
longest = 0

n=2:  is 1 in num_set? No  → sequence-start!
      length=1
        is 3 in num_set? Yes → length=2
        is 4 in num_set? Yes → length=3
        is 5 in num_set? Yes → length=4
        is 6 in num_set? No  → stop
      longest = max(0, 4) = 4

n=3:  is 2 in num_set? Yes → skip (not a sequence-start)
n=4:  is 3 in num_set? Yes → skip
n=5:  is 4 in num_set? Yes → skip

n=10: is 9 in num_set? No → sequence-start!
      length=1
        is 11 in num_set? No → stop immediately
      longest = max(4, 1) = 4   (unchanged)

n=20: is 19 in num_set? No → sequence-start!
      length=1
        is 21 in num_set? No → stop immediately
      longest = max(4, 1) = 4   (unchanged)
```

**Final result:** `longest = 4` — matches the expected output.

**Why this is fast:** numbers like `3`, `4`, and `5` never enter their own `while` loop — they're skipped instantly with a single check. Only true sequence-starts (`2`, `10`, `20`) run the `while` loop, and the total number of steps taken across *all* the while loops combined can never exceed `n`, because every number in the set gets "walked over" by a while loop at most once, as part of the one sequence it truly belongs to. That's what keeps the algorithm at `O(n)` overall, despite having a loop nested inside a loop.

### Complexity Analysis

| Approach | Time | Space |
|---|---|---|
| Sort, then scan | O(n log n) | O(n) |
| Hash set, sequence-starts only | O(n) | O(n) |

### Edge Cases

**Universal checklist:**
- **Empty array:** `nums = []` → `num_set` is empty, the loop never runs, returns `0`.
- **Single element:** `nums = [5]` → `4` isn't in the set, so `5` is a sequence-start with `length = 1`.
- **All identical values:** `nums = [7, 7, 7]` → the set collapses to `{7}`, longest run is `1`.
- **Already sorted / reverse sorted:** doesn't matter — the algorithm never looks at input order, only set membership.
- **Negative numbers:** `nums = [-3, -2, -1, 0]` → sequence-start logic works identically; `-3 - 1 = -4` not in set, counts up to `0`.

**Section-Specific Edge Cases:**
- **Duplicates inside a run:** `nums = [1, 2, 2, 3]` → `set(nums)` collapses the repeated `2` before the loop even starts, so duplicates never inflate the count.
- **Multiple disjoint runs:** `nums = [1, 2, 3, 100, 101]` → two sequence-starts (`1` and `100`), longest correctly returns `3`, not `5`.
- **A run that starts at the very first number checked but isn't actually the longest:** the `for n in num_set:` iteration order is arbitrary in Python, so the algorithm must (and does) check every sequence-start, not stop at the first one found.

> **Simple rule:** whenever a problem needs "does the *value* X exist?" instead of "does *position* i hold X?", reach for a set before reaching for a sort — sorting is `O(n log n)`, a set turns existence checks into `O(1)`.

---

### Key Takeaway

> Don't count every number — count only from true sequence-starts (`n - 1` missing from the set). That single filter is what turns an apparent nested-loop `O(n²)` shape into real `O(n)` work, because each number only ever gets walked once, as part of the one sequence it belongs to.

### Real-World Application

Log timestamp analysis — given a scattered set of second-level timestamps from a server log, finding the longest unbroken stretch of activity (no gaps) is exactly this problem: throw every timestamp into a set, find where each unbroken stretch begins, and count forward. The same pattern shows up in version-number gap detection and in merging fragmented ID ranges during data reconciliation.

### Variation: A Common Alternative Implementation

You'll often see this problem solved with a slightly different version of the same algorithm:

```python
class Solution:
    def longestConsecutive(self, nums: List[int]) -> int:
        numSet = set(nums)
        longest = 0

        for n in nums:
            # check if its the start of a sequence
            if (n - 1) not in numSet:
                length = 0
                while (n + length) in numSet:
                    length += 1
                longest = max(length, longest)
        return longest
```

Two small differences from the version above — both harmless, but worth understanding.

**Difference 1: Looping over `nums` instead of `numSet`**

This version loops over the **original list** (`nums`), which may contain duplicates, instead of the **set** (`numSet`), which has duplicates already removed.

This causes a bit of repeated, wasted work — if `4` appears three times in `nums`, the loop processes `n=4` three separate times. But each repeat check (`if (n-1) not in numSet`) is still O(1) and correctly identifies non-starts, so it just gets skipped instantly each time. Correctness and the overall O(n) time complexity are unaffected — looping over the set instead just avoids the redundant re-checks.

**Difference 2: `length = 0` instead of `length = 1`**

Tracing with `n = 2`, `numSet = {2, 3, 4, 5, 10, 20}`:

```
length=0: is 2+0=2 in numSet? Yes (trivially — n is always in the set) → length=1
length=1: is 2+1=3 in numSet? Yes → length=2
length=2: is 2+2=4 in numSet? Yes → length=3
length=3: is 2+3=5 in numSet? Yes → length=4
length=4: is 2+4=6 in numSet? No  → stop
Final length = 4
```

Starting at `length=0` spends its first loop iteration confirming that `n` itself is in the set — which is always trivially true, since `n` came from the set/list to begin with. It's a harmless extra check; the final `length` still comes out identical to starting at `length=1`.

**Summary:**

| Difference | Impact |
|---|---|
| Loop over `nums` vs `numSet` | Wasted repeated checks on duplicates — correctness and time complexity unaffected |
| `length = 0` vs `length = 1` | One extra trivially-true check per sequence-start — final answer identical either way |

Both versions are correct, run in O(n), and are functionally equivalent — this is a stylistic variation you'll commonly encounter across different explanations of the same algorithm.
