# Recursion: Stack and Time Complexity

*Blind 75 · Python Fundamentals for LeetCode · Topic 15.1*

---

## Introduction

In the last lesson, we traced recursive calls as a tree and saw that recursion has an ascending (calling) phase and a descending (returning) phase. This lesson explains **what actually happens in memory** during those two phases — and uses that to work out how much time and memory a recursive function costs.

---

## How Recursion Uses a Stack

A running program's memory is commonly pictured as three regions:

- **Code** — the compiled instructions for every function. Fixed, never changes.
- **Stack** — grows and shrinks as functions are called and return.
- **Heap** — dynamically allocated memory. Not relevant to this example.

Every time a function is called — recursive or not — an **activation record** (also called a **stack frame**) is created on the stack. It holds that call's own local variables. When the function returns, its activation record is removed.

For `fun1(3)` calling itself down to `fun1(0)`, watch the stack grow one frame per call (blue), then shrink back as each call finishes and returns (each frame marked and removed in reverse order — last pushed, first removed):

<Figure title="Stack Frames: Push and Pop" caption="Each call pushes a new frame toward the heap; each return pops the most recently pushed frame first (LIFO) — exactly why it's called a stack.">
  <StackAnimDiagram />
</Figure>

**Walking through it:**

- `main` starts — its frame is created, holding `x = 3`.
- `main` calls `fun1(3)` — a new frame is pushed, holding `n = 3`.
- Since `n > 0`, it prints `3`, then calls `fun1(2)` — another frame pushed, `n = 2`.
- This continues down to `fun1(0)` — one frame per call, each stacked above the last.
- `fun1(0)`: the base condition fails, so it does nothing and returns immediately. **Its frame is removed first** — the most recently pushed frame is always the first one popped.
- Control returns to `fun1(1)`'s frame, which finishes and is removed next, then `fun1(2)`'s, then `fun1(3)`'s, and finally `main`'s.

This is exactly a **Last In, First Out (LIFO)** structure — the same stack you already met as a data structure. Recursion doesn't just resemble a stack; the language runtime is literally using one to keep track of every paused, in-progress call.

## Memory Consumption (Space Complexity)

Count the activation records created for `fun1(3)`: `fun1(3)`, `fun1(2)`, `fun1(1)`, `fun1(0)` — **4 frames**, each holding one variable, `n`.

In general, for `fun1(n)`, calls run from `n` down to `0` — that's **`n + 1` calls**, so **`n + 1` activation records**.

Each record holds one integer, so total memory is proportional to `n + 1`. Since Big-O keeps only the **highest-degree term** of a formula (here `n + 1` has degree 1 — its highest term is `n`), the space complexity is:

**O(n)**

**The takeaway:** recursive functions are memory-consuming — every call sits on the stack, waiting, until the calls below it finish and return. A plain loop, by contrast, doesn't accumulate frames like this — it reuses the same single stack frame throughout.

---

## Same Stack, Either Version

Recall `fun1` (print, then call) and `fun2` (call, then print) from the last lesson. Their activation records are **identical** — both create one frame per call, holding `n`. The only difference is *when* the value stored in that frame gets used:

- `fun1` uses `n` immediately, **before** pushing the next frame (ascending phase).
- `fun2` pushes all its frames first, then uses each `n` **as its frame is being popped** (descending phase) — which is exactly why the values in the stack are still there and available, ready to be printed on the way back out.

Same stack size, same **O(n)** space either way — the order of operations changes the output, not the memory cost.

## Time Complexity — Frequency Count Method

The first way to measure time is the **Frequency Count Method**: count how many times each statement executes (its *frequency*), then add them up.

The basic rule for measuring time: **assume every statement takes one unit of time** to execute — regardless of what machine it runs on, the same way $1 is "one unit" of currency no matter its real-world purchasing power. If a statement runs multiple times, count how many times.

`fun1` does one meaningful thing repeatedly: `printf`. From the tracing tree (recursion tree), it prints once per call — `3`, then `2`, then `1` — **3 units of time** for `n = 3`.

For a general `n`, that's **`n` units of time** — so the time complexity is also:

**O(n)**

---

## Time Complexity via Recurrence Relation

There's a second, more formal way to reach the same answer: write a **recurrence relation** — an equation defining the time for `fun1(n)` in terms of the time for a smaller call, `fun1(n-1)` — then solve it.

**Building the recurrence:** let `T(n)` be the time taken by `fun1(n)`. Add up every statement inside:

- `if (n > 0)` — 1 unit
- `printf(...)` — 1 unit
- `fun1(n - 1)` — **not** 1 unit. It's a call to the same function with a smaller input, so it costs whatever `fun1` itself costs at `n - 1`: that's `T(n - 1)`.

```text
T(n) = T(n-1) + 1 + 1
     = T(n-1) + 2      (n > 0)
T(0) = 1                (just checking the condition, then returning)
```

This is solved using the **induction method** — also called the **successive substitution method**: keep substituting the recurrence into itself until it bottoms out at the known base case. To make the algebra simpler to follow, replace the constant `2` with a generic constant, `1` — this won't change the final order, only the exact constant:

<Figure title="Successive Substitution" caption="Keep replacing T(n-1) with its own definition until it bottoms out at the known base case, T(0) = 1.">
  <RecurrenceAnimDiagram />
</Figure>

**Reading the derivation:** each substitution replaces `T(n-1)` with `T(n-2) + 1`, then `T(n-2)` with `T(n-3) + 1`, and so on — the pattern after `k` substitutions is `T(n) = T(n-k) + k`. We stop substituting once `n - k` reaches `0` — the point where the base case tells us the exact answer, `T(0) = 1`. Setting `n - k = 0` means `k = n`, so:

```text
T(n) = T(n - n) + n = T(0) + n = 1 + n
```

Same result as the frequency count method — **O(n)**. Two different roads, same destination, which is a good sanity check that the answer is right.

## How This Connects to Other Data Structures

The stack you just watched being pushed and popped isn't a coincidence limited to recursion — it's the same **Stack** data structure covered earlier, doing exactly what it always does: LIFO.

- **Queue (FIFO)** — the natural counterpart. Where recursion/DFS-style traversal relies on a stack, breadth-first traversal (BFS) relies on a queue instead, processing things in the order they were discovered rather than reversing back through them.
- **Linked List** — connects to recursion even more directly: a list is naturally *defined* recursively (a list is either empty, or one node followed by a smaller list), which is why reversing or searching a linked list is often written recursively — each call handles one node, then recurses on "the rest of the list."
- **Heap** — the priority-queue data structure, not the memory region discussed above (worth not confusing the two, since this lesson used "Heap" for the memory region). Operations like `heapify` repeatedly fix one node and then recurse into the affected child, the same push-down/pop-back shape seen here.

**Is this a first step toward non-linear DSA?** Yes — in an important sense. Recursion itself is still operating on a linear call stack, but it's the essential technique that makes **non-linear structures** — **Trees** and **Graphs** — tractable at all. A tree is naturally defined the same recursive way a linked list is ("a node, plus smaller trees as children"), and almost every standard tree or graph traversal (DFS, in-order/pre-order/post-order, backtracking) is written recursively, using precisely the ascending/descending, push/pop mental model built in this lesson. Master this, and trees and graphs stop feeling like a new kind of hard problem and start feeling like a natural extension of what you already know.

## Summary

- Every function call — recursive or not — creates an **activation record** on the **stack**, holding its local variables.
- Calls push frames on the way in (**ascending**); returns pop them on the way out (**descending**), strictly **Last In, First Out**.
- For `fun1(n)`, there are `n + 1` activation records, so **space complexity is O(n)**.
- `fun1` and `fun2` use identical stack space — only *when* each frame's value is used differs.
- **Time complexity** can be found two ways: the **Frequency Count Method** — counting how many times each statement actually runs (here, `n` prints → O(n)), or writing a **recurrence relation** for the function's cost and solving it by the **induction (successive substitution) method** — both give **O(n)** here.
