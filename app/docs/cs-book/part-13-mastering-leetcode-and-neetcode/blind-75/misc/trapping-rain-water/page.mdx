# Trapping Rain Water

**LeetCode #42 · 🔴 Hard**

*Blind-75 Misc #1 · Bonus problem, outside the core 75*

### Problem Statement

> Given `n` non-negative integers representing an elevation map where the width of each bar is `1`, compute how much water it can trap after raining.

```python
# Example 1
Input: height = [0,1,0,2,1,0,1,3,2,1,2,1]
Output: 6
```

**Constraints:**
- `n == height.length`
- `1 <= n <= 2 * 10⁴`
- `0 <= height[i] <= 10⁵`

### Hint

For any single bar, the water sitting above it is capped by whichever is **shorter**: the tallest wall to its left, or the tallest wall to its right. Before reaching for two pointers, think about how you'd get "tallest wall to the left" and "tallest wall to the right" for *every* position — is there a way to compute each of those once, instead of rescanning from scratch at every index?

### Complete Walkthrough

#### The Key Idea

Picture the input as columns of different heights standing side by side. Water falls from above and settles into the low spots — but only if there are taller walls on **both sides** to hold it in. Water can't be trapped at the edges of the whole structure, since it simply flows off the sides.

How much water can sit above any single bar depends on two things:

1. The **tallest bar to its left** (anywhere to the left, not just the neighbor).
2. The **tallest bar to its right** (anywhere to the right).

Water sits up to whichever of those two is **shorter** — because water always spills over the lower of the two "walls" holding it in. Then the bar's own height is subtracted, since the bar itself takes up some of that space.

**For any position `i`:**

```python
water trapped at i = min(tallest bar to the left of i, tallest bar to the right of i) - height[i]
```

If this comes out negative — meaning the bar itself is taller than the shorter of its two walls — there's no water there, so it contributes `0`.

---

#### <span style={{ color: "#dc2626", fontWeight: 700 }}>Approach 1: Brute Force</span>

For every position, look left to find the tallest bar, look right to find the tallest bar, then apply the formula directly.

```python
def trap(height):
    n = len(height)
    total = 0
    for i in range(n):
        left_max = max(height[:i+1])
        right_max = max(height[i:])
        total += min(left_max, right_max) - height[i]
    return total
```

**Breaking it down:**
- `height[:i+1]` — a slice grabbing everything from the start through position `i`. `max(...)` gives the tallest bar to the left (including `i` itself).
- `height[i:]` — a slice grabbing everything from position `i` to the end. `max(...)` gives the tallest bar to the right.
- `min(left_max, right_max) - height[i]` — the water level, capped by the shorter wall, minus the bar's own height.

**Trace**, with `height = [2, 0, 1]`:

```
i=0: height[:1]=[2] → left_max=2 | height[0:]=[2,0,1] → right_max=2
     water = min(2,2) - height[0] = 2 - 2 = 0

i=1: height[:2]=[2,0] → left_max=2 | height[1:]=[0,1] → right_max=1
     water = min(2,1) - height[1] = 1 - 0 = 1

i=2: height[:3]=[2,0,1] → left_max=2 | height[2:]=[1] → right_max=1
     water = min(2,1) - height[2] = 1 - 1 = 0
```

**Total trapped water = 0 + 1 + 0 = 1**

**Why it fails:** `max()` isn't free — it has to look at every element in the slice to find the biggest one. `max(height[:i+1])` costs `i+1` checks, and `max(height[i:])` costs `n-i` checks. Adding this up across every position `i` gives roughly `n` units of work, done `n` times — **O(n²) time** overall. Correct, but too slow for large inputs.

**Space:** O(1) — no real auxiliary data structure is built. The temporary slices created for each `max()` call are fleeting byproducts of the operation, not a persistent structure the algorithm relies on across iterations.

---

#### <span style={{ color: "#2563eb", fontWeight: 700 }}>Approach 2: Precomputed Left-Max and Right-Max Arrays</span>

Instead of recalculating `max()` from scratch at every position, calculate all left-max and right-max values **once each**, store them, and look them up — the same prefix/suffix pattern used in Product of Array Except Self.

```python
def trap(height):
    n = len(height)
    if n == 0:
        return 0

    left_max = [0] * n
    right_max = [0] * n

    left_max[0] = height[0]
    for i in range(1, n):
        left_max[i] = max(left_max[i-1], height[i])

    right_max[n-1] = height[n-1]
    for i in range(n-2, -1, -1):
        right_max[i] = max(right_max[i+1], height[i])

    total = 0
    for i in range(n):
        total += min(left_max[i], right_max[i]) - height[i]

    return total
```

**Pass 1 — Build `left_max`:** `left_max[i]` stores the tallest bar seen so far, from the start through position `i`. Each value builds on the previous one — no rescanning needed.

**Pass 2 — Build `right_max`:** the mirror image, built backward — `right_max[i]` stores the tallest bar from position `i` through the end.

**Pass 3 — Combine:** the same formula as before, but `left_max[i]` and `right_max[i]` are now instant lookups.

**Trace**, with `height = [2, 0, 1]`:

```
Pass 1 — left_max:
left_max[0] = height[0] = 2
i=1: left_max[1] = max(left_max[0], height[1]) = max(2, 0) = 2
i=2: left_max[2] = max(left_max[1], height[2]) = max(2, 1) = 2
left_max = [2, 2, 2]

Pass 2 — right_max:
right_max[2] = height[2] = 1
i=1: right_max[1] = max(right_max[2], height[1]) = max(1, 0) = 1
i=0: right_max[0] = max(right_max[1], height[0]) = max(1, 2) = 2
right_max = [2, 1, 1]

Pass 3 — combine:
i=0: min(2,2) - height[0] = 2 - 2 = 0
i=1: min(2,1) - height[1] = 1 - 0 = 1
i=2: min(2,1) - height[2] = 1 - 1 = 0
```

**Total = 0 + 1 + 0 = 1** — matches the brute-force result.

**Why this is faster:** three separate passes through the array, each doing a fixed, constant amount of work per position. Three passes of O(n) still adds up to **O(n) time overall**.

**Space:** this version genuinely builds real auxiliary data structures — `left_max` and `right_max` are two full arrays, each sized `n`, persisting across the whole algorithm. So this costs **O(n) space**.

---

#### <span style={{ color: "#16a34a", fontWeight: 700 }}>Approach 3: Two Pointers (Optimal)</span>

<span style={{ color: "#2563eb", fontWeight: 700 }}>The precomputed-arrays version is already O(n) time, but still uses O(n) space. The two-pointer trick eliminates that extra memory entirely.</span>

**The key realization:** <span style={{ color: "#2563eb", fontWeight: 700 }}>we don't need to know the *exact* `left_max` and `right_max` for every position ahead of time</span> — only which side is currently shorter, which can be tracked as two pointers move toward each other from opposite ends.

```python
def trap(height):
    left, right = 0, len(height) - 1
    left_max, right_max = height[left], height[right]
    total = 0

    while left < right:
        if left_max < right_max:
            left += 1
            left_max = max(left_max, height[left])
            total += left_max - height[left]
        else:
            right -= 1
            right_max = max(right_max, height[right])
            total += right_max - height[right]

    return total
```

**Breaking it down:**
- `left, right = 0, len(height) - 1` — two pointers starting at opposite ends.
- `left_max, right_max = height[left], height[right]` — <span style={{ color: "#2563eb", fontWeight: 700 }}>instead of full arrays, track just the single tallest value seen so far on each side.</span>
- `while left < right:` — continue until the pointers meet.
- `if left_max < right_max:` — always move the pointer on the **shorter** side. The water level there is capped by the shorter wall, and we already know which side is currently shorter.
- Moving the left pointer: update `left_max` if the new bar is taller, then add `left_max - height[left]` as water trapped at this position. <span style={{ color: "#2563eb", fontWeight: 700 }}>Since `left_max < right_max` on this branch, the water level is safely capped by `left_max` alone.</span>
- The `else` branch mirrors this logic for the right side.

**Why moving the shorter side is always safe:** if `left_max < right_max`, there's guaranteed to be a wall somewhere on the right at least as tall as `right_max`. So no matter what lies between the current `left` position and the actual right edge, the water level at `left` can never be limited by anything on the right — `right_max` alone already exceeds `left_max`. This is what allows resolving the left side using only `left_max`, without needing the precise right-side maximum — the entire trick behind O(1) space.

**Trace**, with `height = [2, 0, 1]`:

```
left=0, right=2
left_max = height[0] = 2
right_max = height[2] = 1
total = 0

Iteration 1: left(0) < right(2)? Yes.
left_max(2) < right_max(1)? No → else branch
right -= 1 → right = 1
right_max = max(1, height[1]) = max(1, 0) = 1
total += right_max - height[1] = 1 - 0 = 1
total = 1

Iteration 2: left(0) < right(1)? Yes.
left_max(2) < right_max(1)? No → else branch
right -= 1 → right = 0
right_max = max(1, height[0]) = max(1, 2) = 2
total += right_max - height[0] = 2 - 2 = 0
total = 1

Iteration 3: left(0) < right(0)? No → loop ends.
```

**Final total = 1** — matches both previous versions.

### Complexity Analysis

| Approach | Time | Space |
|---|---|---|
| Brute force (`max()` on slices) | O(n²) | O(1) *(no real aux. structure)* |
| Precomputed `left_max`/`right_max` arrays | O(n) | O(n) *(two real arrays)* |
| Two pointers | O(n) | O(1) *(no real aux. structure)* |

**A note on what counts as "real" auxiliary space:** a real auxiliary data structure is extra data storage deliberately built and kept around — like a list, dictionary, or set — that persists for some or all of the algorithm's runtime and grows as the input grows. In Approach 2, `left_max` and `right_max` are exactly this: two full arrays, sized `n`, built once and relied on throughout. That's genuine O(n) space. In Approach 1, `height[:i+1]` and `height[i:]` create small temporary slices — but these exist only for the instant one `max()` call needs them, then disappear; they aren't something the algorithm builds up or depends on across iterations. A simple test: would you draw this on a whiteboard as "the extra data structure my algorithm uses"? An array built once and queried repeatedly counts. A slice that flashes into existence for one line and vanishes doesn't.

### Edge Cases

**Universal checklist:**
- **Empty array:** not possible under the constraints (`n >= 1`), but a length-1 or length-2 array can never trap water — there's no room for a "middle" bar between two walls, so the answer is always `0`.
- **All same height:** `height = [3, 3, 3, 3]` → every position's `left_max` and `right_max` equal the bar's own height, so `water = 0` everywhere.
- **Already sorted (strictly increasing):** `height = [1, 2, 3, 4]` → each bar is its own tallest wall on one side, nothing to hold water in — total is `0`.
- **Reverse sorted (strictly decreasing):** `height = [4, 3, 2, 1]` → same reasoning mirrored — total is `0`.
- **Numbers at the extremes:** `height[i]` up to `10⁵` — Python ints handle this with no overflow concern, unlike fixed-width integer languages.

**Section-Specific Edge Cases:**
- **A single tall spike with nothing around it:** `height = [0, 0, 5, 0, 0]` — no walls on either side of the spike, so nothing gets trapped despite the tall bar; the flat zeros on both sides cap `left_max`/`right_max` at `0`.
- **A flat valley bounded by walls of equal height:** `height = [3, 0, 0, 3]` → both pointers see the same shorter wall repeatedly; the algorithm still correctly fills the entire valley to level `3`.
- **Water level determined by the far wall, not the nearer one:** `height = [5, 1, 1, 1, 2]` — the water above each middle bar is capped by `min(5, 2) = 2`, not by the closer-looking `5`. This is exactly why both `left_max` and `right_max` must be considered, not just "the nearest tall bar."

> **Simple rule:** whenever a bar's answer depends on "the best value to my left" *and* "the best value to my right" simultaneously, check whether you actually need both exact values at every step — if you only need to know which side is currently smaller, two pointers can replace two full auxiliary arrays.

---

### Key Takeaway

> Water above any bar is never limited by its immediate neighbor — it's limited by the *shorter of the two tallest walls* anywhere to its left and right. Once that's clear, an O(n²) rescan collapses first into two prefix/suffix arrays, and then further into two pointers that never need to store more than a single running maximum on each side.

### Data Structures & Pattern Used

**Data structures used:**
- **Array/List** (`height`) — the same basic structure used throughout, e.g. `nums` in Contains Duplicate, Product of Array Except Self, and Longest Consecutive Sequence.
- **Auxiliary arrays** (`left_max`, `right_max`) — only in Approach 2. The same prefix/suffix array pattern first introduced in Product of Array Except Self, just applied to a `max()` running value instead of a running product.
- **Plain variables, no hash structure** — in the optimal Approach 3, there's no `set()` or `dict` at all, unlike Contains Duplicate (a `set`), Group Anagrams (a `dict`), or Longest Consecutive Sequence (a `set`). This problem is solved with array indexing and a handful of tracking variables instead — a reminder that not every optimal solution needs a hash-based structure.

**Pattern used:** **Two Pointers** — specifically the *converging* variant, where one pointer starts at the far left, one starts at the far right, and they move **toward each other** until they meet.

- **Converging pointers** (used here) — start at both ends, move inward. Also used in Valid Palindrome, Two Sum II (sorted input), 3Sum, and Container With Most Water.
- **Same-direction pointers / sliding window** — both pointers start at the same end and expand/shrink a window as they move forward together.
- **Slow/fast pointers** — commonly used on **linked lists** rather than arrays, for tasks like finding the middle node or detecting a cycle.

The underlying idea — "shrink the search space from both ends based on a comparison" — is the same across all converging two-pointer problems, whether the data structure holding the values is an array (like here) or something else.

### Real-World Application

Picture two lifeguards standing at opposite ends of a long swimming pool with an uneven, bumpy floor, each watching the water level trapped near their own end. At any moment, whichever lifeguard is standing at the **shorter** section of pool wall can immediately calculate the water trapped there — because they know for certain the wall on the *other* side is at least as tall as theirs. That lifeguard steps inward and repeats, and the two keep closing the gap from both ends until they meet — never needing the *exact* height of the far wall, only that it's taller than their own.

The same shape of reasoning shows up in reading a stock's price chart: two local peaks (resistance highs) with a dip between them (a pullback). The "water trapped" at any day in that dip is a rough visual proxy for the *depth of a pullback* within a broader consolidation range — a trader scanning inward from two nearby peaks doesn't need the full price history, only the tallest peak "wall" on each side of the current dip, which is exactly the two-pointer idea applied to price data instead of building heights.
