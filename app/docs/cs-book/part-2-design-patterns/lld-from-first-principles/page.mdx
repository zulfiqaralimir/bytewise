# LLD From First Principles

This chapter builds Low-Level Design up from scratch — not as a list of patterns to memorize, but as a set of first principles that explain *why* those patterns exist in the first place. Each section pairs a precise, technical statement with a plain-English translation, then grounds it in two running examples: a parking lot system and a stock market order system.

## Section 0: What Problem Is LLD Even Solving?

**Technical:** Code that satisfies today's requirements without regard to structure tends to violate the Open/Closed Principle implicitly — it's closed to extension, so new requirements force modification of existing, tested code, increasing regression risk.

<Callout type="tip" title="🗣️ In Plain English">
Basically — if you don't think about design, your code works fine today. But the moment someone says "hey, also add this," you end up ripping open stuff that already worked, and now you might break it. Good design = you can bolt new stuff on without touching the old stuff.
</Callout>

**Parking lot example:** Built for "cars only" → now add motorcycles + different EV pricing.
- Bad design → rewrite half the codebase.
- Good design → add new classes, leave old ones alone.

**Stock market example:** Order system handles only "Buy/Sell market orders" → now add Limit Orders, Stop-Loss, short-selling.
- Bad design → `if/else` chains multiplying everywhere.
- Good design → each order type is its own class, added independently.

<Callout type="info" title="First Principle #1">
LLD exists to make change cheap.
</Callout>
