*High-level modules should not depend on low-level modules — both should depend on abstractions*

## Dependency Inversion (DIP)

**OOP Principles Used:** Abstraction (Type 2 — interfaces), Polymorphism

### Start with an everyday picture: a wall socket, not a hardwired wire

Imagine your lamp was **hardwired directly into your wall** — actual wires soldered straight from the wall into the lamp. If you ever wanted a different lamp, an electrician would need to rewire your wall.

Instead, your wall has a **socket** — a standard plug interface. Any lamp, toaster, or charger that fits the plug shape can be plugged in. <Revision>The wall doesn't care *which specific device* is plugged in — it only cares that the device follows the plug's shape (the "contract").</Revision>

<Callout type="tip" title="🗣️ Conversational">
<Revision>The wall depends on "anything that fits a standard plug," not on "this one specific lamp."</Revision> That's the whole idea of DIP.
</Callout>

### Step 1 — See the problem first, in code (no DIP yet)

```python
class EmailNotifier:
    def send(self, message):
        print(f"Emailing: {message}")


class OrderProcessor:
    def __init__(self):
        self.notifier = EmailNotifier()   # hardwired directly to EmailNotifier

    def process(self, order):
        print("Processing order...")
        self.notifier.send("Your order was processed!")
```

**Technical:** `OrderProcessor` directly creates and depends on the concrete class `EmailNotifier`. This is a **hardwired connection** — like the lamp soldered into the wall.

<Callout type="warning" title="⚠️ What's Wrong Here">
- If tomorrow you also want SMS notifications, or want to swap email for a different provider, you must **open up and edit `OrderProcessor`** — the exact "reopening tested code" problem from Section 0.
- `OrderProcessor`'s job is supposed to be "process orders" — but it's now also tightly stuck to one specific way of sending notifications. It shouldn't need to know or care about *how* notifications are sent.
</Callout>

### Step 2 — Recall the tools you already have (Abstraction Type 2 + Polymorphism)

You already know how to solve "many different implementations, one shared contract" — this is exactly what Type 2 Abstraction and Polymorphism are for (you used this in OCP with `TaxStrategy`).

```python
from abc import ABC, abstractmethod

class Notifier(ABC):
    @abstractmethod
    def send(self, message):
        pass

class EmailNotifier(Notifier):
    def send(self, message):
        print(f"Emailing: {message}")

class SMSNotifier(Notifier):
    def send(self, message):
        print(f"Texting: {message}")
```

<Callout type="tip" title="🗣️ Conversational">
`Notifier` is the "standard plug shape." `EmailNotifier` and `SMSNotifier` are two different devices that both fit that plug shape.
</Callout>

### Step 3 — Make `OrderProcessor` depend on the plug shape, not the specific device

```python
class OrderProcessor:
    def __init__(self, notifier: Notifier):   # depends on the ABSTRACTION, not a specific class
        self.notifier = notifier

    def process(self, order):
        print("Processing order...")
        self.notifier.send("Your order was processed!")
```

**Using it:**
```python
processor1 = OrderProcessor(EmailNotifier())
processor2 = OrderProcessor(SMSNotifier())

processor1.process(order)   # emails
processor2.process(order)   # texts — SAME OrderProcessor class, no editing needed
```

<Callout type="tip" title="🗣️ Conversational">
`OrderProcessor` no longer cares *which* notifier it gets — email, SMS, or something invented next year (WhatsApp, push notification). It just knows: "whatever you are, you can `.send()` a message." That's Polymorphism doing the actual work here, just like in every pillar before this.
</Callout>

**Technical:** `OrderProcessor` (a high-level module) no longer depends on `EmailNotifier` (a low-level, concrete module). Both now depend on the `Notifier` abstraction instead.

### The formal definition — and why it's called "inversion"

**Technical:** High-level modules should not depend on low-level modules; both should depend on abstractions. Abstractions should not depend on details; details should depend on abstractions.

<Callout type="tip" title='🗣️ Conversational — why "inversion"?'>
Normally you'd think the "big important class" (`OrderProcessor`) depends on the "small specific class" (`EmailNotifier`) — that feels like the natural direction. DIP flips (inverts) that: instead, `EmailNotifier` has to conform to what `Notifier` (the abstraction) demands, and `OrderProcessor` only ever talks to `Notifier`. The dependency direction is flipped — the specific class now depends on the shared contract, not the other way around.
</Callout>

### C++ version

```cpp
class Notifier {
public:
    virtual void send(const std::string& message) = 0;
    virtual ~Notifier() {}
};

class EmailNotifier : public Notifier {
public:
    void send(const std::string& message) override {
        std::cout << "Emailing: " << message << std::endl;
    }
};

class SMSNotifier : public Notifier {
public:
    void send(const std::string& message) override {
        std::cout << "Texting: " << message << std::endl;
    }
};

class OrderProcessor {
private:
    Notifier* notifier;   // depends on the abstraction, not a concrete class

public:
    OrderProcessor(Notifier* n) : notifier(n) {}

    void process() {
        std::cout << "Processing order..." << std::endl;
        notifier->send("Your order was processed!");
    }
};
```

### How DIP ties back to everything you've already learned

<Callout type="info" title="🗣️ Conversational">
DIP is really the payoff of everything so far. Abstraction (Type 2) gave you the "plug shape." Polymorphism let different devices plug into it and just work. OCP told you to add new notifiers without editing old code. DIP tells you exactly *where* to put the abstraction in your class relationships — high-level classes should talk to the plug shape, never to the specific device.
</Callout>

</Callout>

## Further Simplification

Hoorain, DIP is usually the **hardest SOLID principle for a beginner**, mainly because the word *dependency* makes it sound more complicated than it is.

Let's start with **zero assumptions about programming** and build it up slowly.

### Dependency Inversion Principle (DIP) — From Zero

The simplest version of DIP is:

> **High-level code should not depend directly on low-level code. Both should depend on an abstraction.**

That sentence is difficult right now, so **don't try to memorize it yet**.

First, let's understand **dependency**.

### 1. What Does "Dependency" Mean?

**Dependency** simply means:

> **One thing needs another thing to work.**

For example, imagine:

```text
Car → Engine
```

A car needs an engine to work.

So we can say:

> **Car depends on Engine.**

In programming, the same idea applies.

Suppose we write:

```python
class Engine:
    def start(self):
        print("Engine started")


class Car:
    def start_car(self):
        engine = Engine()
        engine.start()
```

Here, `Car` directly creates and uses `Engine`:

```python
engine = Engine()
```

So:

```text
Car
 ↓
Engine
```

The `Car` **depends directly on** the `Engine`.

### 2. Why Can This Be a Problem?

Imagine that later we want to use an electric motor instead of an engine.

We create:

```python
class ElectricMotor:
    def start(self):
        print("Electric motor started")
```

Now our `Car` is still written like this:

```python
class Car:
    def start_car(self):
        engine = Engine()
        engine.start()
```

It is **hard-coded** to `Engine`.

If we want to change it to `ElectricMotor`, we have to modify the `Car` class.

That's the problem DIP tries to solve.

### 3. Let's Identify the Two Levels

In this example:

```text
Car
 ↓
Engine
```

`Car` is the **high-level code**.

Why?

Because `Car` represents the main business idea:

> "Start the car."

`Engine` is the **low-level code**.

It handles the specific implementation:

> "How exactly does the engine start?"

So:

```text
High-level
    ↓
   Car

Low-level
    ↓
  Engine
```

The problem is that the high-level `Car` is directly tied to the specific low-level `Engine`.

### 4. DIP Says: Don't Depend Directly on the Specific Thing

Instead of:

```text
Car
 ↓
Engine
```

we want:

```text
       Car
        ↓
   Abstraction
      /     \
 Engine   ElectricMotor
```

Now `Car` doesn't care whether it gets:

- an `Engine`
- an `ElectricMotor`
- or another type of motor

It only cares about the **required behavior**.

### 5. What Is an Abstraction?

This is another word that sounds difficult.

An **abstraction** is simply:

> **A general description of what something should do, without specifying exactly how it does it.**

For example:

```text
"Something that can start"
```

That's an abstraction.

We don't care whether it starts using:

```text
Engine
```

or:

```text
Electric Motor
```

We only care that it can:

```text
start()
```

In Python, we can represent this idea using a base class.

For example:

```python
class Engine:
    def start(self):
        print("Engine started")
```

and:

```python
class ElectricMotor:
    def start(self):
        print("Electric motor started")
```

Both provide:

```python
start()
```

So they share the same expected behavior.

### 6. Dependency Injection

There's another concept that often appears together with DIP:

**Dependency Injection.**

Instead of making `Car` create the dependency itself:

```python
class Car:
    def start_car(self):
        engine = Engine()
        engine.start()
```

we **give the Car its dependency from outside**:

```python
class Car:
    def __init__(self, engine):
        self.engine = engine

    def start_car(self):
        self.engine.start()
```

Now we can do:

```python
engine = Engine()
car = Car(engine)

car.start_car()
```

Or we can use an electric motor:

```python
motor = ElectricMotor()
car = Car(motor)

car.start_car()
```

The `Car` doesn't need to change.

That's a huge improvement.

### 7. What Actually Happened?

Originally:

```text
Car
 │
 │ directly creates
 ▼
Engine
```

The Car was saying:

> "I specifically need an Engine."

After our change:

```text
Car
 │
 │ receives
 ▼
something that can start
```

The Car is now saying:

> "I don't care what you are. Just give me something that can `start()`."

That's much more flexible.

### 8. The DIP Connection

Now we can understand the original definition:

> **High-level modules should not depend on low-level modules. Both should depend on abstractions.**

Our example becomes:

```text
           Abstraction
          "can start()"
           ↑       ↑
           │       │
         Car     Engine
                 /
        ElectricMotor
```

More conceptually:

```text
              Abstraction
             /           \
            /             \
        Car             Engine
                         /
                 ElectricMotor
```

The important idea is that `Car` doesn't directly depend on a specific implementation.

### 9. Why Is It Called "Inversion"?

This is the part that confuses many beginners.

Originally:

```text
High-level Car
       ↓
Low-level Engine
```

The high-level code depends directly on the low-level code.

DIP changes the direction of the dependency.

Instead of:

```text
Car → Engine
```

we have:

```text
Car → Abstraction ← Engine
```

The **abstraction sits between them**.

Both sides depend on the abstraction.

That's why it is called **Dependency Inversion**.

### 10. A Very Simple Real-Life Analogy

Imagine you own a phone.

You don't need to know exactly how electricity is generated.

You simply expect:

> "I need a power source."

You can plug your phone into:

```text
Wall charger
Power bank
Car charger
```

Your phone doesn't need to be redesigned for each one.

Why?

Because they all provide the expected thing:

```text
Power
```

Think of:

```text
Phone → Power interface ← Charger / Power Bank
```

The phone depends on the **general requirement**, not one specific implementation.

That's the basic idea behind DIP.

### 11. The Most Important Distinction

Don't confuse **DIP** with **Dependency Injection**.

They are related, but they aren't exactly the same thing.

**Dependency Inversion Principle** — a **design principle**:

> High-level code should depend on abstractions rather than directly depending on low-level implementations.

**Dependency Injection** — a **technique** for achieving that flexibility:

> Give an object the dependency it needs from outside instead of making it create the dependency itself.

For example:

```python
class Car:
    def __init__(self, engine):
        self.engine = engine
```

The `engine` is being **injected** into `Car`.

### 12. The Beginner-Friendly Definition

If the formal definition feels too difficult, remember this:

> **DIP means: Don't make your important/high-level code depend directly on a specific implementation. Instead, make it depend on a general abstraction.**

Or even simpler:

> **"Depend on what something can do, not on exactly how it does it."**

For our example:

```text
❌ Car → Engine

✅ Car → "Something that can start"
             ↑
          Engine
             or
       ElectricMotor
```

That is the core idea of **Dependency Inversion Principle**.
