*A subclass must be a safe, surprise-free substitute for its base class*

## Section 9: SOLID Principles — Liskov Substitution (LSP)

**OOP Principles Used:** Inheritance, Polymorphism

### Start with an everyday picture: a universal remote

Imagine a TV remote that's supposed to work for "any TV."

- You buy a new TV, plug it in, use the same remote.
- Pressing the power button now turns up the volume instead of turning the TV on/off.
- The remote is no longer a safe substitute — you expected the same behavior, and didn't get it.

### Step 1 — Inheritance, plain recall

```python
class Order:
    def execute(self):
        print("Order executed")

class MarketOrder(Order):
    def execute(self):
        print("Market order executed")
```

**Technical:**
- `MarketOrder` derives from `Order`, inheriting its interface.
- This establishes an IS-A relationship.

<Callout type="tip" title="🗣️ Conversational">
`MarketOrder` is built from `Order`'s blueprint plus its own tweaks. So `MarketOrder` "is-a" `Order`. Nothing new here — just a reminder from [Section 4](/docs/cs-book/part-2-design-patterns/chapter-1/4-inheritance).
</Callout>

### Step 2 — Polymorphism, plain recall

```python
orders = [MarketOrder()]
for order in orders:
    order.execute()
```

**Technical:**
- The loop invokes `.execute()` on each object without checking its concrete type.
- It relies on runtime dispatch to resolve the correct method.

<Callout type="tip" title="🗣️ Conversational">
The loop just says "do your thing" without asking what type it's holding. It trusts that whatever object it has knows how to execute itself correctly. That trust is the whole point of [Polymorphism](/docs/cs-book/part-2-design-patterns/chapter-1/5-polymorphism).
</Callout>

### Step 3 — Introduce a subclass that breaks the trust

```python
class CancelledOrder(Order):
    def execute(self):
        raise Exception("Cannot execute a cancelled order!")
```

```python
orders = [MarketOrder(), CancelledOrder()]
for order in orders:
    order.execute()
```

**Technical:**
- `CancelledOrder` satisfies the inheritance relationship syntactically.
- But its override does not preserve the behavioral contract established by `Order.execute()`.
- Calling it raises an exception instead of completing execution.

<Callout type="warning" title="⚠️ What's Wrong Here">
The loop trusted that calling `.execute()` on *any* `Order` works — that's Polymorphism's whole deal. `CancelledOrder` inherits from `Order` (Inheritance), so the loop accepts it without question. But `CancelledOrder.execute()` doesn't do what `Order.execute()` promised — it crashes instead. Substituting `CancelledOrder` in wherever an `Order` was expected broke the program.
</Callout>

### The derivation — why LSP exists at all

**Technical:**
- LSP exists because Inheritance permits a subclass to occupy any slot typed for its base class.
- Polymorphism resolves the call at runtime without verifying behavioral equivalence.
- Together, these create the possibility of a substitution that is syntactically valid but semantically broken — the exact failure mode LSP is defined to prevent.

<Callout type="tip" title="🗣️ Conversational">
LSP only exists because Inheritance lets a subclass sneak into a slot expecting the base class, and Polymorphism blindly trusts that slot. If either pillar didn't exist, LSP would have nothing to protect.
</Callout>

### The formal definition

**Technical:**
- Objects of a subclass should be substitutable for objects of the base class, without altering the correctness of the program.
- A subclass must honor the behavior contract the base class promises.

<Callout type="tip" title="🗣️ Conversational">
If `MarketOrder` inherits from `Order`, you should be able to use a `MarketOrder` object anywhere an `Order` was expected. It should behave the way `Order` promised — no surprises. The same must hold for `CancelledOrder`, and it currently doesn't.
</Callout>

### A preview of the fix

**Technical:**
- A cleaner design avoids attaching `execute()` to classes that cannot fulfill its contract.
- Cancellation status should be modeled separately, or `Order`'s interface should be segregated so "executable" and "cancellable" aren't conflated into one contract.

<Callout type="info" title="🗣️ Conversational">
Instead of forcing `CancelledOrder` to pretend it can execute at all, only put `execute()` on classes that can actually execute. Handle cancellation some other way. We'll see this properly once we reach Interface Segregation.
</Callout>

</Callout>
